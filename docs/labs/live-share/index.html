Side Lab: Real-Time Collaborative Coding with VS Code Live Share

Practice professional pair programming in one shared VS Code workspace without replacing Git, branches, commits, or pull requests.

Time: 25–35 minutes · People: ideally two learners · Curriculum status: optional and not required for React progress

Why Live Share Exists

Screen sharing lets another person watch. Live Share lets them enter the host’s current workspace through their own VS Code: navigate independently, follow another participant, co-edit permitted files, join debugging, view shared servers, and use shared terminals when the host allows it. Teams use it when conversation and immediate shared context are more useful than exchanging patches back and forth.

Excellent for synchronous work

  • Pair programming
  • Mentoring and onboarding
  • Debugging a difficult problem together
  • Technical interviews
  • Classroom learning and code walkthroughs

Git still handles durable work

  • Independent feature development
  • Commit history and authorship
  • Asynchronous review
  • Automated pull-request checks
  • Merging, reverting, and release history

Current-Information Audit

Live Share is not Git

A guest works against the host’s shared workspace. Live Share does not replace branches, commits, pull requests, or a durable review trail. Commit the resulting work through the team’s normal Git workflow.

The guest does not need a full clone

Live Share gives the guest remote access to the host-approved workspace without synchronizing the entire repository first. The host’s machine and workspace remain the source of the session.

Following is optional

Participants may follow the host’s cursor for a walkthrough, then stop following and navigate independently. Independent navigation is normal, not a disconnected session.

Terminal access is powerful

A shared terminal runs on the host machine. Start read-only, never expose secrets, and grant read/write access only to a trusted collaborator for a specific reason.

Sign-in affects permissions

The host signs in to share. Microsoft documents anonymous/read-only guest scenarios, but a guest should sign in with GitHub or Microsoft when edit access is required.

UI labels can move

The extension remains available, but some official documentation contains legacy platform/version wording and VS Code surfaces evolve. The Command Palette names in this lab are the most reliable route when a status-bar button looks different.

Learning Objectives

  • Explain real-time collaborative coding
  • Install and configure VS Code Live Share
  • Host and join a collaboration session
  • Edit one project simultaneously
  • Use following, independent navigation, and shared terminals safely
  • Choose Live Share or Git branches based on the collaboration need
One-step rule: complete only the visible step. Select Done, I have a question, or I hit an error. The next step stays hidden until the current step is complete.

Step 1 of 6

Step 1/6 — Install, Sign In, and Establish Roles

Concept first: Live Share is a VS Code extension. Both people install it; the host must authenticate to create a trusted session, and a guest should authenticate when edit access is needed.

Application
Visual Studio Code on both computers.
Who acts
Host and guest.
Menu/command
Open Extensions with Ctrl+Shift+X (macOS: ⇧⌘X). Search for Live Share published by Microsoft and select Install. Then open the Command Palette with Ctrl+Shift+P (macOS: ⇧⌘P), type Live Share: Sign In, and complete GitHub or Microsoft authentication.
Success looks like
The Microsoft Live Share extension shows Installed, VS Code recognizes your signed-in identity, and searching the Command Palette for Live Share returns collaboration commands.
Decide now: one person is the host whose local project will be shared; the other is the guest. The guest should not open a different copy of the same repository for this exercise.
Stay on Step 1.

Ask: “In Step 1, I am the host/guest. I expected Live Share commands, but I see ____. What should I check next?” Include your operating system and whether the extension says Installed.

Troubleshoot one check at a time:
  1. Confirm the publisher is Microsoft and the extension identifier is MS-vsliveshare.vsliveshare.
  2. Reload VS Code from the Command Palette with Developer: Reload Window.
  3. Search the Command Palette for Live Share before relying on a status-bar icon.
  4. If browser sign-in does not return to VS Code, finish authentication, return to VS Code manually, and run Live Share: Sign In once more.

Do not continue until Live Share commands appear.

Step 2/6 — Host the Project and Create an Invite

Concept first: the host shares the currently opened workspace. The invite link grants access to a live session, so treat it like a temporary credential and send it only to the intended guest.

Application
Visual Studio Code on the host computer.
Who acts
Host only.
Menu/command
Use File → Open Folder… and open the project you intend to share. Open the Command Palette and run Live Share: Start Collaboration Session. If VS Code asks for guest approval or workspace trust, review the prompt and approve only the expected project and person.
Success looks like
VS Code reports that a collaboration session started, the Live Share participants area appears, and an invitation link is copied or offered for copying.
Host safety check: close files containing secrets, review the shared root, and do not paste the invitation into a public channel.
Stay on Step 2.

State whether the command is missing, sign-in is requested, the session starts without a link, or workspace trust is blocking it.

Troubleshoot incrementally:
  1. Confirm an actual folder—not an empty VS Code window—is open.
  2. Run Live Share: Sign In and retry the start command.
  3. Open the Live Share view and look for Copy Collaboration Link if the clipboard notification disappeared.
  4. If connectivity fails, record the exact Live Share notification before changing firewall or network settings.

Step 3/6 — Join as the Guest

Concept first: the guest enters the host’s remote workspace. They do not need to clone the repository, install the project dependencies, or open their own competing copy first.

Application
A browser and Visual Studio Code on the guest computer.
Who acts
Guest, with host approval if prompted.
Menu/command
Open the private invitation link and allow it to launch VS Code. If browser launching fails, copy the link, open the Command Palette, run Live Share: Join Collaboration Session, and paste the link. Sign in if edit access is required.
Success looks like
The guest sees the host’s shared file tree and both participants appear in Live Share. The host sees the expected guest identity and approves it if approval is enabled.
Permission signal: if the guest can view but not edit, confirm they are signed in and that the host did not intentionally start a read-only session.
Stay on Step 3.

Tell the host whether you see no workspace, a read-only workspace, an approval wait, or a connection failure.

Troubleshoot incrementally:
  1. Confirm the host session is still active and request a freshly copied link.
  2. Use the Command Palette join command instead of the browser handoff.
  3. Confirm the guest is signed in for read/write access.
  4. Have the host inspect the participant approval notification before restarting the session.

Step 4/6 — Follow, Navigate Independently, and Co-Edit

Concept first: following is useful for a walkthrough; independent navigation is useful for investigation. Professional pairs switch between both modes instead of forcing everyone to stare at one cursor.

Application
Visual Studio Code on host and guest.
Who acts
Both participants.
Menu/command
The host creates a harmless practice file named collaboration-practice.js. In the Live Share participants list, the guest selects the host to follow. The host opens the practice file and types const pair = [];. The guest stops following by opening another file, returns to the practice file independently, and adds one name inside the array. The host adds the second name.
Success looks like
Both participants see each other’s cursor/presence, edits appear in near real time, following moves the guest with the host, and independent navigation does not disconnect the session.
const pair = ['host-name', 'guest-name'];
Professional workflow: say what you intend to edit before typing in the same lines. One person can drive while the other navigates, researches, reviews, or prepares the next small change.
Stay on Step 4.

Describe whether the problem involves following, independent navigation, cursor visibility, or edit permission.

Troubleshoot incrementally:
  1. If edits are blocked, recheck the guest’s sign-in and session permissions.
  2. If following does nothing, select the participant from the Live Share participant list again.
  3. If the file is missing, confirm the host created it inside the shared workspace root.
  4. If edits conflict, stop typing, choose one driver, restore the intended line, and retry with verbal handoff.

Step 5/6 — Share a Terminal Safely

Concept first: a shared terminal is not a simulated guest terminal—it runs on the host machine with the host’s files and environment. Read-only access supports teaching with less risk; read/write access enables pairing but should be temporary and trusted.

Application
Visual Studio Code on host and guest.
Who acts
Host shares; guest observes first.
Menu/command
The host opens the Command Palette and runs Live Share: Share Terminal, or opens the Live Share view and selects the terminal-sharing action if the wording differs. Choose read-only first. In that terminal, the host runs a harmless command such as git status. The guest opens the shared terminal from the Live Share view and observes the output.
Success looks like
The guest sees the host’s terminal output but cannot type in read-only mode. Both understand that commands execute against the host workspace.
Never demonstrate with secrets. Do not print environment variables, tokens, SSH material, password files, browser profiles, or unrelated directories. Grant read/write only when the host trusts the guest and the task truly requires joint command entry.
Stay on Step 5.

Ask whether the issue is finding Share Terminal, choosing permissions, opening the terminal as guest, or seeing command output.

Troubleshoot incrementally:
  1. Confirm the host has a local integrated terminal open.
  2. Look in both the Command Palette and Live Share view because labels can move.
  3. Confirm the guest opens the shared terminal, not a new local terminal.
  4. If the guest can type unexpectedly, stop sharing and recreate the terminal as read-only.

Step 6/6 — Verify, End the Session, and Preserve Work with Git

Concept first: Live Share is temporary synchronous access. Git creates the durable record after the pairing session: what changed, why, who reviewed it, and how it enters the main branch.

Application
Visual Studio Code on both computers; terminal on the host.
Who acts
Both verify; host ends the session.
Menu/command
Confirm both names remain in collaboration-practice.js. The host runs git diff -- collaboration-practice.js. Discuss whether to keep or delete the practice file. Then the host opens the Command Palette and runs Live Share: End Collaboration Session.
Success looks like
The guest is disconnected, the host’s local file retains the final edits, the collaboration link no longer provides the live workspace, and any real work is ready for a normal branch/commit/pull-request workflow.

Live Share or Git?

NeedUseReason
Two people solve one problem nowLive ShareImmediate shared context and conversation
Work continues independentlyGit branchIsolation and durable history
Teammates review laterPull requestAsynchronous discussion and automated checks
Mentor demonstrates and learner drivesLive ShareFast role switching without environment setup
Production change must be mergedGit + pull requestReviewable, testable, reversible record
Stay on Step 6.

Ask whether the uncertainty concerns preserving edits, ending the session, or choosing Live Share versus Git for the next task.

Troubleshoot incrementally:
  1. If the guest remains connected, confirm the host ran the end-session command rather than only closing a file.
  2. If edits disappeared, check the host’s actual workspace and git status; the host filesystem is authoritative.
  3. If the practice file should not remain, remove only that explicitly named file through your normal editor or Git workflow.
Setup verified: you installed Live Share, created and joined a session, followed and navigated independently, co-edited one file, observed a safe shared terminal, and ended the session.

3-Question Recall Quiz

1. Your teammate will implement a feature over two days and request review tomorrow. Which tool should hold that work?

2. A guest wants to watch the host explain one file, then investigate another file without disconnecting. What should they use?

3. What is the safest first permission for a teaching terminal?

Memory Anchor

Live Share is the shared workbench; Git is the permanent ledger.

Use the workbench to solve something together now. Use the ledger to preserve, review, merge, and reverse the result.
