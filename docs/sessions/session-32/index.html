Folder Organization

Organize code so a change has one obvious home, imports describe ownership, and moving files does not change behavior.

// One defensible solution
function groupByOwner(files) {
  return files.reduce((groups, file) => {
    const owner = file.startsWith('ui/') ? 'shared' : file.split('/')[0];
    groups[owner].push(file);
    return groups;
  }, { countries: [], favorites: [], shared: [] });
}
This solution groups feature files by owner and reserves shared for the UI primitive.

9. Reflection Questions

  1. What makes a folder boundary useful?

    It groups files that change for the same reason, giving maintainers one predictable place to investigate.

  2. When should code move into shared UI?

    Only after multiple features use the same behavior and API; premature sharing creates coupling around guesses.

  3. Why move one dependency slice at a time?

    Small moves keep broken imports easy to locate and make behavior-preserving verification possible.

10. What Breaks If This Boundary Is Ignored?

  • Responsibilities drift across unrelated modules.
  • Safe changes become harder to verify and explain.
  • Future learners inherit coupling without its original reasoning.

11. What Engineering Concept Was Learned Today

Architecture is a map of ownership: good folders reduce the distance between a change request and the files it affects.
