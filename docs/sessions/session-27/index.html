Why We Test and What to Test

Tests protect observable behavior, not implementation trivia. Learn to choose assertions that survive safe refactoring and fail when users would notice a regression.

Estimated time: 40–50 minutes · Concept session — no application code changes

Your task: Implement chooseBehaviorTests. Return the three checks that should survive a harmless internal refactor.

function chooseBehaviorTests(possibleTests) {
  return possibleTests.filter(test =>
    test.includes("heading shows") ||
    test.includes("changes the visible count") ||
    test.includes("returns a changed count to zero")
  );
}

console.log(chooseBehaviorTests(possibleTests));

Lesson connection: You just separated user-visible contracts from implementation machinery—the central decision behind valuable tests.

1. Learning Objectives

  • Distinguish unit, component, integration, and end-to-end scope
  • Select behaviors worth protecting based on user-visible risk
  • Avoid testing state variables, function names, and incidental markup
  • Use Arrange–Act–Assert to structure a test
  • Explain how behavior-focused tests support refactoring

3. The Concept — Confidence Without Handcuffs

Tests are executable examples of promised behavior. For CountryCard, high-value risks include missing prop output, controls that cannot be found, and interactions that fail to update the screen. Low-value targets include the exact hook used, local function names, and the number of wrapper divs.

Test targetValueReason
Heading shows country nameHighUser-visible prop behavior
Click changes count textHighCritical interaction
Handler named handleClickLowPrivate implementation
Outer class nameUsually lowStyling detail, unless contractual

4. Guided Analysis

Lab objective: Design a behavior-first CountryCard test plan without changing application code.
End state: A prioritized test matrix separates user-visible contracts from replaceable implementation details.
1

Step 1 of 5

List user-visible behaviors

Write observable outcomes, not hooks or markup.

1. Known name and region props appear.
2. Clicking "Click Me" increases the displayed count.
3. Clicking "Reset" after increments returns the count to zero.
2

Step 2 of 5

Write Arrange, Act, and Assert

Describe one behavior before selecting test APIs.

Behavior: increment displayed count

Arrange: Render CountryCard with known props.
Act: Find "Click Me" by role and click once.
Assert: The page displays "Clicked 1 times".
3

Step 3 of 5

Remove brittle assertions

Contrast private details with the public contract.

Brittle:
- useState is called exactly once.
- The wrapper keeps class country-card.
- The handler is named handleClick.

Durable:
- Clicking increment changes visible count 0 → 1.

Reason: internals may change while behavior stays correct.
4

Step 4 of 5

Rank by regression risk

Prioritize by user impact and likelihood.

1. Render supplied country data — users may see wrong information.
2. Increment visible count — primary interaction may fail.
3. Reset from nonzero — recovery action may fail.

CountryCard renders valid props without throwing.
5

Step 5 of 5

Build the test matrix

Give every test one diagnostic purpose.

| Behavior | Action | Expected output | Regression |
| Render props | Open card | Japan and Asia | Prop wiring |
| Increment | Click Click Me | Clicked 1 times | Event/state |
| Reset | Increment, Reset | Clicked 0 times | Reset transition |

Each row should fail for one clear reason.

8. Post-Coding Quiz

Question 1 of 5

Which CountryCard test best survives a harmless markup refactor?

The semantic heading and its content express behavior without pinning wrapper structure.
Question 2 of 5

A Reset button is renamed visually to Clear. Which test contract would intentionally fail?

If the accessible name Reset is part of the intended UI, changing it is observable and should update or fail the test intentionally.
Question 3 of 5

Why prefer a role query for a button over a CSS selector?

Semantic queries align tests with user-facing accessibility rather than styling hooks.
Question 4 of 5

One test renders, clicks increment, clicks reset, changes props, and checks five labels. What is the main cost?

Focused tests produce more specific failures and make the protected behavior obvious.
Question 5 of 5

What should determine whether a behavior deserves a test first?

Testing priority should follow risk, not implementation size or convenience.

9. Reflection Questions

  1. Which current CountryCard detail is most tempting but least useful to test?

    Implementation details such as hook choice, handler names, CSS classes, or wrapper structure are tempting but fragile. Tests gain more value by checking the information and interactions a user can observe.

  2. What regression would hurt a user most?

    Missing or incorrect country information, a broken increment action, or a reset that leaves the displayed count wrong would directly block or mislead the user.

  3. How can a test suite make refactoring safer instead of harder?

    Assert public behavior with semantic queries and avoid private implementation details. Then internal structure can change freely while focused tests still catch changes to the user-facing contract.

10. What Breaks Without Testing Principles?

  • Low-value assertions create noisy failures.
  • Important behavior may remain unprotected.
  • Safe refactors become unnecessarily expensive.

11. What Engineering Concept Was Learned Today

Tests should maximize confidence in observable behavior while minimizing coupling to replaceable implementation.
