Layer 3 Session 18.8 JavaScript + React

JavaScript, React, and the Invisible Handoff

Why React Doesn't Re-render Immediately — Session 18.5 taught you what a closure is. Session 19 is about to show you a render counter and a batching experiment that only make sense if you already believe one strange fact: calling setCount does not update anything — it just asks React to update something, later. This short session is the missing link between "I called a function" and "the screen changed," and it is entirely about timing, not new JavaScript syntax.

Estimated time: 20–25 minutes

1. Learning Objectives

  • Explain that JavaScript executes one thing at a time and cannot be interrupted mid-function
  • Explain that setCount() schedules an update rather than performing one immediately
  • Describe React's internal update queue as hidden — something your code never reads or writes directly
  • Trace the full handoff: the event handler runs to completion, JavaScript returns control, and only then does React process queued updates and re-render
  • Explain why this handoff is the actual mechanism behind Session 19's batching and stale-closure behavior

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

Inside a click handler, you call setCount(6) and then immediately call console.log("after") on the next line. Which runs first?

setCount only schedules an update. The very next line of your handler still runs normally, and React doesn't re-render until the whole handler finishes.
Question 2 of 5

Can React pause your event handler halfway through and re-render immediately?

JavaScript's single-threaded execution model means a running function always finishes before anything else gets a turn — React included.
Question 3 of 5

What does calling setCount(6) actually do, the moment it's called?

setCount's real job is registering a request. Nothing about the screen changes at the exact moment it's called.
Question 4 of 5

After a click handler finishes running completely, what happens next?

The handler finishing is the signal — JavaScript hands control back, and only then does React look at what's pending and act on it.
Question 5 of 5

Why does a console.log placed right after setCount() print before React re-renders?

That console.log is just another line inside the still-running handler. It executes before the handler returns, which is before React ever gets a turn.

3. The Concept — Two Cooperating Systems, Taking Turns

There are two cooperating systems here: JavaScript and React. They take turns. While JavaScript is executing your event handler, React cannot interrupt it. Only after JavaScript finishes does React process its queued updates. That's the entire idea of this session — everything else is detail.

Not a JavaScript internals lesson: we are not covering the browser event loop, microtasks, or the call stack in detail here. The only goal is naming the handoff between "your code is running" and "React does its thing" — enough to make Session 19 feel obvious instead of magical.

What you'd naturally expect

Most code you've written so far behaves like a simple chain — one function directly calls the next, in order, and each one's work is done by the time it returns: 

A()
↓
B()
↓
C()
↓
D()

React quietly breaks this pattern the moment a state update is involved:

A()
↓
B()
↓
C()

----------- JavaScript finishes -----------

React:
D()

D() — the re-render — is not called from inside C(). It happens later, from an entirely different system, after your own code has completely finished running. There is no line in your handler that calls it. That missing, invisible line is exactly what this session names.

The full handoff, traced step by step

Click
↓
JavaScript starts handleClick()
↓
setCount(...)
↓
React records the update request
↓
handleClick continues running
↓
handleClick finishes
↓
JavaScript returns control
↓
React processes its queued updates
↓
React calls CountryCard() again
↓
New render
↓
New closures

Two things worth slowing down on: setCount(...) only hands React a request — it does not call the component again itself. And handleClick continues running after that request is made — nothing about calling setCount stops or pauses the rest of the function.

Why This Feels Weird

  • setCount() looks exactly like an ordinary function call.
  • Normally, calling a function means it does its work right then.
  • But setCount() only asks React to do work later.
  • React hides its scheduler and its update queue — you never see either one directly.
  • The actual re-render happens later, outside your handler's visible call chain.

You're not missing something obvious by finding this confusing — the syntax is deliberately designed to look like an ordinary call, while behaving completely differently underneath. Once you know the handoff exists, the confusion has a name, and Session 19's batching and stale-closure behavior stop feeling like magic.

4. Lab

Lab objective: Add a console.log before and after setCount inside handleClick, and confirm both logs print before the screen visibly updates.
1

Add logs around setCount in CountryCard's handleClick

function handleClick(event) {
  console.log("before setCount, count is", count);
  setCount(count + 1);
  console.log("after setCount — this still runs before any re-render");
}
2

Open DevTools and click the button once

Read the console output top to bottom. Both log lines appear before you see the count update on screen, and both appear on every single click, in the same order, every time.

3

Predict, then verify: does "after setCount" ever see the new count?

Before running it again, guess what count equals inside the "after setCount" log line. Then check — it's still the OLD value, because count is a constant captured for this render, and this render hasn't been replaced yet.

4

Remove the logs once you've confirmed the behavior

This lab is a diagnostic experiment, not a permanent feature — revert handleClick back to just calling setCount(count + 1) before committing.

8. Post-Coding Quiz

Question 1 of 5

In the lab, the "after setCount" console.log still showed the OLD count value. Why?

This is the direct link to Session 18.5's closures: count doesn't mutate in place — it stays the same until an entirely new render hands you a new one.
Question 2 of 5

Why can't React simply re-render the instant setCount is called, mid-handler?

This isn't a React design choice you could argue with — it's a direct consequence of how JavaScript itself executes code, one function to completion at a time.
Question 3 of 5

What is React's update queue, functionally?

The queue exists purely internally — its entire job is holding requests until the moment JavaScript hands control back to React.
Question 4 of 5

Given today's handoff, why does calling setCount twice in one handler not produce two separate re-renders?

Both requests land in the same queue before JavaScript ever returns control, so React only gets one chance to act on all of them together — this is the seed of Session 19's batching.

10. What Breaks If This Code Is Removed?

  • This is a concept-only session — no permanent code changes: nothing in the actual app depends on today's lab, since the console.log statements are deliberately temporary and reverted before committing.
  • Skipping this session's mental model: nothing crashes, but Session 19's render counter and batching experiment will feel like arbitrary trivia instead of the direct, predictable consequence of the handoff explained here.
  • Misunderstanding the handoff going forward: expecting setCount to update synchronously leads directly to the stale-closure bugs Session 19 demonstrates — this session exists so that bug has an explanation instead of feeling random.

11. What React Concept Was Learned Today

Today you learned: JavaScript and React are two cooperating systems that take turns. JavaScript always finishes running your event handler before React ever gets a turn, and setCount only schedules a request in React's hidden update queue rather than performing an update itself. That handoff — not any new syntax — is the entire reason batching and stale closures exist.
