Session 17 and 18 built a click counter and named its handlers, but we never actually looked at what "re-render" means or when it happens. Today: a render counter that proves exactly when CountryCard re-runs, and a hands-on experiment with React's automatic batching that exposes a very common state-update bug before you ever write it yourself.

3. The Concept — What Actually Triggers a Re-render

A re-render is just React calling your function again

Nothing mystical happens. React keeps a reference to your component function and, when it decides a re-render is needed, it calls that function again — the same way any JavaScript function gets called again. The new JSX it returns gets diffed against what's currently on screen, and only the actual differences get applied to the real DOM.

What triggers it: a state update, every time

function handleClick(event) {
  console.log(event.type, event.target)
  setCount(count + 1)   // <- this line is the ONLY thing that schedules a re-render
}

Calling a state setter — setCount, in our case — is what schedules a re-render. It doesn't matter what value you pass it; even setCount(count) (the exact same value) schedules a re-render, because React can't cheaply know in advance whether the value actually changed without first re-rendering to check.

What does NOT trigger it: mutating a plain variable

function CountryCard({ name, region }) {
  let localCounter = 0;   // a plain variable, not state

  function handleClick() {
    localCounter = localCounter + 1;  // React has no idea this happened
    console.log(localCounter);         // this prints correctly...
    // ...but the screen never updates, because nothing told React to re-render
  }
}

Automatic batching

In React 18 and 19, multiple state updates inside the same event handler are batched — grouped into a single re-render instead of one re-render per setCount call. This isn't just an optimization detail; it changes how you have to reason about calling a setter more than once in a row. 

function handleClick() {
  setCount(count + 1);
  setCount(count + 1);
  // Even though setCount is called twice, React batches this into
  // ONE re-render — and both calls read the exact same "count" from
  // this render's closure, so the net effect is +1, not +2.
}

The stale-closure trap

Every time CountryCard renders, count is a brand new const captured for that render — it never changes for the lifetime of that particular render's handleClick closure. Both setCount(count + 1) calls above read the same count, compute the same new value, and hand React the same instruction twice. React doesn't add them together; the second call just overwrites the first with an identical result.

The fix, previewed but not required today: a "functional update" — setCount(c => c + 1) — passes a function instead of a value. React calls that function with whatever the latest pending state actually is, so calling it twice really does add up to +2. We are not refactoring to this pattern in today's lab; the goal today is understanding why the plain version behaves the way it does.

The render counter as a proof tool

// Module-level — declared OUTSIDE the component function, once
let renderCount = 0;

function CountryCard({ name, region }) {
  const [count, setCount] = useState(0);

  renderCount++;
  console.log(`CountryCard render #${renderCount} — ${name}, count is now ${count}`);

  // ...
}

renderCount lives outside the component, at module scope, so it survives across every render without being reset — and incrementing it is exactly the kind of plain mutation from Section 3 that does not itself trigger anything. It's a passive instrument, not a feature: it only tells you how many times React has already decided to call this function.

4. Lab

Lab objective: Add a module-level render counter to CountryCard, verify it counts real re-renders, then run a predict-then-observe experiment with a doubled setCount call to see batching and the stale closure in action.
1

Add the render counter

import { useState } from "react";

let renderCount = 0;

function CountryCard({ name, region }) {
  const [count, setCount] = useState(0);

  renderCount++;
  console.log(`CountryCard render #${renderCount} — ${name}, count is now ${count}`);

  // ...handleClick, handleReset, JSX unchanged
}
2

Verify: click and watch the count climb by exactly one per click

Open DevTools console. Click "Click me" on one card three times. You should see three log lines, render numbers climbing by one each time, count going 1, 2, 3. Click the other card — its own log lines start from wherever the shared renderCount currently is (it's shared across every card), but that card's own count starts fresh at 1.

3

Predict, then experiment: double the setCount call

Before editing anything: write down what you think will happen to count per click if handleClick calls setCount(count + 1) twice.

function handleClick(event) {
  console.log(`Action:${event.type},\n Target attr:`, event.target)
  setCount(count + 1)
  setCount(count + 1)   // temporarily added for this experiment
}

Save, click the button once, and read the log. Was your prediction right? count should have gone up by exactly 1, not 2.

4

Revert the experiment

Remove the duplicated setCount(count + 1) line so handleClick is back to calling it once. Keep the render counter — that part is permanent for this session.

10. What Breaks If This Code Is Removed?

  • Remove the render counter: No functional change to the app — it's a diagnostic tool, not a feature. But you lose visibility into when and how often re-renders actually happen.
  • Leave the doubled setCount(count + 1) in place: Not a crash, just a silent bug — the button would appear to only work "half as well" as intended, incrementing by 1 when a developer might have expected 2, for a reason that isn't obvious without today's session.
  • Move renderCount inside the component function: It would reset to 0 on every single render, making it useless as a running counter — the same mistake as Question 1 of the post-quiz.

11. What React Concept Was Learned Today

Today you learned: a re-render is React re-invoking your component function, only state updates trigger it, multiple updates in one handler are batched into one re-render, and each render's state values are captured in a closure that stays constant for that render.
