Controlled Inputs

Every input we've touched so far has been a button — click in, click out, nothing typed. Today CountryList gets a real text input, and we learn the one pattern that makes React "own" what's typed into it: value tied to state, onChange tied to a setter. We are not filtering anything yet — that's next.

Estimated time: 35–40 minutes

1. Learning Objectives

  • Explain the difference between an uncontrolled and a controlled input
  • Wire an input's value prop to a piece of state
  • Wire that same input's onChange to a setter that reads event.target.value
  • Trace the full loop: keystroke → onChange → setState → re-render → value prop reflects the new state
  • Recognise why searchTerm living inside CountryList is a temporary, soon-to-be-wrong location for it

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

What makes an input "controlled" in React?

The defining trait is the value prop being driven by state. Without it, the browser's own DOM tracks the typed text and React has no visibility into it.
Question 2 of 5

Given <input value={searchTerm} onChange={handleSearchChange} />, what fires handleSearchChange?

onChange on a text input fires on every value-changing keystroke, not just on blur or submit — this is different from some other frameworks' "change" event.
Question 3 of 5

Inside the onChange handler, how do you read the new text the user just typed?

Same event object pattern from Session 18, applied to a new property: target.value holds the input's current text at the moment the event fired.
Question 4 of 5

If you set value={searchTerm} on an input but never call a setState function in onChange, what happens when you try to type?

Once value is tied to state, that state is the ONLY thing that can change what's displayed. A controlled input with no updating setState is a classic "frozen input" bug.
Question 5 of 5

After today's lab, does typing in the search box change which countries are shown in the list?

Today's milestone is strictly the controlled-input mechanics. Filtering needs searchTerm to live somewhere both the input AND the list can reach — that's Session 21.

3. The Concept — Who Owns the Value?

Uncontrolled: the DOM owns it

<input type="text" placeholder="Search countries..." />

This is a perfectly valid input, and plain HTML has always worked this way — the browser tracks what's typed internally, and if you want to read it from JavaScript you'd have to reach into the DOM directly (document.querySelector or a ref, which we haven't covered). React has no idea what's in this box at any given moment.

Controlled: React state owns it

import { useState } from 'react';

function CountryList() {
  const [searchTerm, setSearchTerm] = useState('');

  function handleSearchChange(event) {
    setSearchTerm(event.target.value);
  }

  return (
    <input
      type="text"
      value={searchTerm}
      onChange={handleSearchChange}
      placeholder="Search countries..."
    />
  );
}

Two props make this input "controlled": value, which tells the input exactly what to display (driven by state, not by whatever the user last typed), and onChange, which is how React finds out the user tried to change it. Miss either half and the pattern breaks.

Why not just use the uncontrolled version and read it later?

You could — for a single simple field, uncontrolled inputs are genuinely fine. But once React owns the value, you get things for free that are hard to bolt on afterward: you can validate or transform text as it's typed, clear the field programmatically by setting state, and — the reason we're doing it today — share that value with other parts of the component tree, which Session 21 needs.

A subtle bug to watch for: if you set value={searchTerm} but forget the onChange handler entirely, React logs a console warning and the input will appear "stuck" — every keystroke gets immediately overwritten back to the current state, because nothing is telling React the state should change.

Quotes around searchTerm inside {} would make it a string literal, not a reference to the state variable — a classic curly-brace/quote mixup.

Why does every single keystroke cause a re-render of CountryList, given what Session 19 taught about what triggers re-renders?

This directly connects back to last session: onChange itself doesn't cause anything; it's the setState call inside the handler that does.

What is the actual type of event.target.value inside handleSearchChange?

Text input values are always strings, regardless of what characters were typed — the same "everything from an input is text" idea applies here as anywhere else in JavaScript.

Filtering purely within CountryList would technically work for today's app, but the syllabus is deliberately building toward lifting state up in Session 21 so state can be shared — the real motivating problem, not a hard technical blocker yet.

10. What Breaks If This Code Is Removed?

  • Remove onChange, keep value: The input becomes visibly frozen — every keystroke is instantly reverted, since nothing updates the state that value is bound to.
  • Remove value, keep onChange: The input becomes uncontrolled again — it will type normally by itself, but searchTerm state silently drifts out of sync with what's actually displayed, since nothing ever reads it back into the DOM.
  • Remove useState('') entirely: searchTerm is undefined, and React will warn about switching an input from uncontrolled to controlled (or vice versa) as its value prop flips between defined and undefined across renders.

11. What React Concept Was Learned Today

Today you learned: a controlled input ties its value to state and its onChange to a setter, making React — not the DOM — the single source of truth for what's displayed.
