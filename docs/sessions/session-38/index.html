A successful network connection does not guarantee valid or useful data.

1. Learning Objectives

  • Distinguish network failure from unsuccessful HTTP status
  • Check response.ok before trusting JSON
  • Validate and normalize external records
  • Keep API field names out of presentation components
  • Test success and failure at the service boundary

3. The Concept — Translate at the Border

Big picture: Treat HTTP and third-party JSON as unreliable inputs, then convert successful responses into one stable Country shape the React UI can trust.

HTTP success has several gates

What problem does this solve? fetch resolves for many 404 and 500 responses.

Why should I care? Status, parsing, and shape checks are separate responsibilities.

What would happen if React did not have this? Without those gates, an error page can be treated as country data.

9. Reflection Questions

  1. What problem did this lesson solve?

    A service boundary converts unreliable HTTP and vendor data into a stable contract the UI can understand.

  2. Why should a professional care?

    The boundary makes failures easier to locate and future changes easier to verify without rereading the entire application.

  3. What cost or tradeoff remains?

    Every new boundary, state, or document adds something developers must learn. Keep it only while it makes the behavior clearer than the simpler alternative.

10. What Breaks If This Boundary Is Ignored?

  • The failure appears far from the responsibility that caused it.
  • Unrelated code changes together because ownership is unclear.
  • A visual check can pass while an important contract is broken.
  • The next learner inherits a rule without understanding its reason.
