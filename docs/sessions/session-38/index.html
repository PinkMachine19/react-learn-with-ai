Fetch and Real APIs

Treat HTTP and third-party JSON as unreliable inputs, then convert successful responses into one stable Country shape the React UI can trust.

Estimated time: 75–95 minutes · Milestone: Build a trustworthy service boundary
Visual Primer · 9 different concepts
Optional Warm-Up5-Minute Wake-Up Challenge: Inspect an Untrusted Record

Give yourself five minutes. List everything that could go wrong before this object becomes a Country: { cca3: 'GHA', name: { common: 'Ghana' }, population: 34000000 }. You may use paper or a scratch file; do not modify the entire React app. 

fetch → check response.ok → parse JSON → validate fields → normalize to { id, name, population }

A successful network connection does not guarantee valid or useful data.

1. Learning Objectives

  • Distinguish network failure from unsuccessful HTTP status
  • Check response.ok before trusting JSON
  • Validate and normalize external records
  • Keep API field names out of presentation components
  • Test success and failure at the service boundary

2. Pre-Coding Quiz

Need 4/5 to proceed. Every option describes a believable coding decision, so use the reason—not answer length—to choose.

Question 1 of 5

Why must code check response.ok after fetch resolves?

A completed HTTP exchange is not the same as a successful status. fetch rejects network failures but commonly resolves error-status responses.
Question 2 of 5

Which failure happens before an HTTP response exists?

A connectivity or DNS failure rejects fetch without an HTTP response. The other cases received a response and must be interpreted.
Question 3 of 5

What does await response.json() guarantee?

response.json parses the body. It does not check response.ok, confirm an array, or validate the records inside it.
Question 4 of 5

Why convert cca3 and name.common inside the service?

The service translates provider-specific fields once. Components can use id and name without knowing how the outside API names them.
Question 5 of 5

The parsed JSON is an object instead of an array. Where should that be rejected?

Reject the wrong top-level shape beside the parsing code. That produces a clear error before the bad value travels into rendering.

Why should I care? Status, parsing, and shape checks are separate responsibilities.

7. Code Review Checklist

8. Post-Coding Quiz

Question 1 of 5

A server returns 500 with valid JSON. What should fetchCountries do?

Status checking comes before trusting the body as country data. Valid JSON can still describe a server error.
Question 2 of 5

One item has name: null. What is the most useful response?

Handle malformed outside data at the service. Otherwise every component must defend itself against the same provider mistake.
Question 3 of 5

Which module should know the API field name cca3?

Provider vocabulary belongs in the service. The rest of the app should receive the simple internal id field.
Question 4 of 5

Which test most directly protects response.ok handling?

A mocked 500 response exercises the status branch directly. UI tests do not prove that the service rejects bad HTTP statuses.
Question 5 of 5

Why test malformed JSON shape separately from a network rejection?

One failure means no usable response arrived; the other means a response arrived with unusable data. Separate tests show which protection failed.

9. Reflection Questions

  1. What problem did this lesson solve?

    A service boundary converts unreliable HTTP and vendor data into a stable contract the UI can understand.

  2. Why should a professional care?

    The boundary makes failures easier to locate and future changes easier to verify without rereading the entire application.

  3. What cost or tradeoff remains?

    Every new boundary, state, or document adds something developers must learn. Keep it only while it makes the behavior clearer than the simpler alternative.

10. What Breaks If This Boundary Is Ignored?

  • The failure appears far from the responsibility that caused it.
  • Unrelated code changes together because ownership is unclear.
  • The page can look correct while another file receives the wrong input or result.
  • The next learner inherits a rule without understanding its reason.
