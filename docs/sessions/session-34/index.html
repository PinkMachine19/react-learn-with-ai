Custom Hooks

Move the country-search behavior out of App without moving the screen. Learn what a custom hook really is, why its name starts with use, and when creating one is—or is not—worth the extra file.

Estimated time: 65–85 minutes · Milestone: extract and verify useCountrySearch

1. Learning Objectives

  • Explain the problem a custom hook solves before defining the term
  • Separate stateful search behavior from the screen that displays it

2. Pre-Coding Quiz

Answer from understanding, not vocabulary. Need 4/5 to proceed.

Question 1 of 5

What is the main reason to extract the current search logic from App?

The search pieces belong together because they describe one job. In plain English: the hook gives the “how search works” code one named home; it is not a React size rule or automatic performance trick.
Question 2 of 5

Which part should remain in App?

The hook owns mechanics; App owns what learners see. In plain English: the hook can hand App searchTerm and results, but App still decides where the input and country cards appear.
Question 3 of 5

Why should filteredCountries usually not be another state variable?

Filtered countries contain no new information; they are the answer to a calculation. In plain English: if we know the full list and the typed text, we can always recreate the result, so a second stored copy can only become outdated.
Question 4 of 5

Why must custom hooks be called at the top level?

React connects stored state to the order in which hooks are called. In plain English: if a condition skips hook number two, React can confuse which saved value belongs to later calls.
Question 5 of 5

What makes a useful return object for this hook?

The return object is the hook’s public menu. In plain English: App should receive searchTerm, a way to change it, filtered countries, and count—not private ingredients it never uses.

3. The Concept — A Custom Hook Is a Named Box for Stateful Behavior

Concept A — What is a custom hook?

What problem does this solve? Related React behavior is mixed into a component that also has to render a screen.

Why should I care? Giving the behavior its own name makes App easier to read and the behavior easier to reuse or test.

What would happen if React did not have this? The app would still work. We would leave state in components, pass more props, or use older composition patterns. Custom hooks make organization easier; they do not unlock secret React powers.

Problem → Idea → Analogy → React example → Professional reason

Problem: App owns search behavior AND screen markup
   ↓
Idea: move only search behavior into useCountrySearch
   ↓
Analogy: take one recipe out of a crowded notebook
   ↓
React: const search = useCountrySearch(countries)
   ↓
Professional reason: one named behavior is easier to change and test

Technical: a custom hook composes React hooks into reusable stateful logic.

In plain English: it is a normal JavaScript function that is allowed to call hooks like useState, then hands useful values and functions back to a component.

Concept B — Why does the name start with use?

What problem does this solve? React tools and developers need to recognize functions that follow hook rules.

Why should I care? The name warns us not to call the function inside conditions, loops, or random callbacks.

What would happen without the naming rule? Code could still run, but lint tools could not reliably protect us from broken call order.

App renders
  │
  ├── 1. useCountrySearch(...)
  │       └── useState(...)
  └── 2. any later hook

Next render: the order must remain 1 → 2

Wait… why? React does not remember state by your variable name. It remembers “first hook call,” “second hook call,” and so on. Stable order lets it return the right saved value.

Concept C — Stored state versus calculated values

What problem does this solve? Duplicate state can disagree with itself.

Why should I care? Fewer sources of truth mean fewer mysterious bugs.

What would happen if we stored everything? We would need extra code to synchronize filteredCountries and resultCount every time countries or searchTerm changed.

Store this:
searchTerm = "ja"

Calculate these:
filteredCountries = countries filtered by "ja"
resultCount = filteredCountries.length

Technical: filteredCountries and resultCount are derived values.

In plain English: they are answers we can calculate from information we already have, so we should not keep another copy that might become wrong.

Concept D — The hook contract

What problem does this solve? App needs to use search without knowing every internal detail.

Why should I care? A small return object makes the connection understandable.

What would happen without a clear contract? App might depend on internal setters and temporary variables, making future changes risky.

countries
   │
   ▼
useCountrySearch
   │
   ├── searchTerm
   ├── handleSearchTerm
   ├── filteredCountries
   ├── resultCount
   └── clearSearch
   │
   ▼
App chooses the JSX

Technical: the returned object is the hook’s public API.

In plain English: it is the small menu of search tools App is allowed to use.

4. Guided Lab

Lab objective: move the existing country-search behavior from App into useCountrySearch without changing what the learner sees or how search behaves.

The honest tradeoff

This refactor adds a file and an import. If search stayed tiny and App were its only permanent user, leaving it in App could be clearer. We are extracting it because the state, calculation, count, and clear action form one understandable behavior—and because later screens could reuse that behavior without copying it.

Do not memorize “logic must leave components.” Memorize: extract when related behavior has a useful name and the new boundary makes the code easier to understand.

Step 1 of 5

Mark the behavior boundary in App

What problem does this solve? Moving lines blindly can separate code that belongs together or move screen code that should stay.

Why should I care? We first identify the job before creating the file.

What happens without this step? The hook can become a random storage box rather than one understandable behavior.

MOVE to the hook:
  searchTerm state
  handleSearchTerm
  filteredCountries
  resultCount

KEEP in App:
  h1, input, paragraph, CountryList JSX

Simple analogy: move the recipe, not the dining room. Search mechanics are the recipe; App’s markup is how the meal is presented.

Why professionals do it: naming the boundary before editing prevents “utility” files that contain unrelated leftovers.

2

Step 2 of 5

Create useCountrySearch.js

What problem does this solve? The behavior needs a named home that can still use React state.

Why should I care? A normal helper cannot call useState; a custom hook can.

What if custom hooks did not exist? Search state would remain in App even if pure filtering moved to a helper.

// src/features/countries/useCountrySearch.js
import { useState } from 'react';

function useCountrySearch(countries) {
  const [searchTerm, setSearchTerm] = useState('');

  function handleSearchTerm(event) {
    setSearchTerm(event.target.value);
  }

  // More behavior arrives in Step 3.
}

export default useCountrySearch;

In plain English: the hook receives the country list, remembers what the user typed, and provides a function that updates that memory.

3

Step 3 of 5

Calculate results instead of storing copies

What problem does this solve? Stored results could disagree with the current text.

Why should I care? The calculation always uses the newest inputs.

What if we stored filteredCountries too? We would need synchronization code and could accidentally show stale countries.

const filteredCountries = countries.filter(country =>
  country.name.toLowerCase().includes(searchTerm.toLowerCase())
);

const resultCount = filteredCountries.length;

function clearSearch() {
  setSearchTerm('');
}

Simple analogy: do not store yesterday’s calculator answer beside today’s numbers. Recalculate the answer from the numbers currently on the screen.

4

Step 4 of 5

Return the hook’s small public contract

What problem does this solve? App cannot use values trapped inside another function.

Why should I care? Returning a small object makes the handoff explicit.

What if we returned every internal detail? App would become tied to how the hook works instead of what it provides.

return {
  searchTerm,
  handleSearchTerm,
  filteredCountries,
  resultCount,
  clearSearch
};
Hook owns                     App receives
─────────                     ────────────
state           ───────────▶  searchTerm
update logic    ───────────▶  handleSearchTerm
calculation     ───────────▶  filteredCountries
count           ───────────▶  resultCount
reset action    ───────────▶  clearSearch
5

Step 5 of 5

Use the hook in App and verify behavior

What problem does this solve? App must reconnect the extracted behavior to its input, count, and list.

Why should I care? A refactor is successful only when users experience the same working search.

What if the hook works alone but App connects it incorrectly? The page can still break, so test both the behavior and its integration.

import useCountrySearch from './features/countries/useCountrySearch.js';

const {
  searchTerm,
  handleSearchTerm,
  filteredCountries,
  resultCount,
  clearSearch
} = useCountrySearch(countries);

Keep the existing JSX, but connect it to these returned values. Optionally add <Button onClick={clearSearch}>Clear search</Button>.

Run the feedback loop

npm test
npm run dev
  • Typing ja should show Japan.
  • The result count should match the visible list.
  • Clearing should restore the full list.
  • The hook must be called unconditionally near the top of App.

After the lab: what actually improved?

App is not magically faster. The improvement is that a reader can now understand the screen at two levels:

App.jsx
  "What does the page display?"

useCountrySearch.js
  "How does country searching behave?"

If another screen later needs the same search behavior, it can call the hook and choose completely different JSX. If no second screen ever appears, the hook can still be worthwhile because it gives a complicated behavior a clear name—but that benefit must outweigh the cost of another file.

8. Post-Coding Quiz

Question 1 of 5

The hook returns JSX for the search input and country cards. What concern has moved into the wrong place?

The hook should provide behavior while App chooses the interface. In plain English: returning JSX turns the hook back into a hidden component and prevents another screen from presenting search differently.
Question 2 of 5

Search results stay stale after the countries prop changes. What implementation should you inspect?

Copied results require manual synchronization with every input. In plain English: if results are calculated directly from the newest countries and searchTerm, they cannot remain yesterday’s answer.
Question 3 of 5

App calls useCountrySearch only when countries.length is greater than zero. Why is that unsafe?

React associates state with call position. In plain English: skipping a hook on one render can shift the numbered state slots and make React return the wrong saved values.
Question 4 of 5

What is the best reason to test clearSearch?

Callers rely on clearSearch to restore empty search text and full results. In plain English: test what the hook promises to users of the hook, not every private line used to produce that promise.
Question 5 of 5

When should this behavior probably stay inside App instead?

Extraction has a navigation and API cost. In plain English: do not create a hook because “hooks are professional”; create one when naming and separating the behavior genuinely helps readers or reuse.

9. Reflection Questions

  1. Why is useCountrySearch a hook rather than a normal helper?

    It owns searchTerm state through useState, so it must follow hook rules. A pure filter function that only receives countries and text could be a normal helper because it would not use React state.

  2. What did App keep, and why?

    App kept headings, input markup, count text, Button placement, and CountryList. Those choices describe the screen. The hook provides values and actions but does not decide how the interface looks.

  3. What is the cost of this custom hook?

    Readers must follow an import into another file and learn its return contract. The separation is worthwhile only when the behavior is coherent enough that its name and boundary reduce more confusion than they create.

10. What Breaks If the Hook Is Removed?

React itself does not break. The search behavior must move back into App or another component.

  • App again owns state, filtering, counting, clearing, and markup in one place.
  • Another screen would need copied logic or a different shared solution.
  • Hook-focused tests would move to component tests.
  • The user-facing search can still work if the behavior is moved correctly.

This is important: architecture tools organize working behavior; they are not required rituals.

11. What Engineering Concept Was Learned Today

A custom hook gives related React behavior a reusable name and contract while leaving the screen free to choose its own JSX.

In plain English: move the search engine, not the dashboard.
