Layer 3 Session 18.5 JavaScript Prerequisite

JavaScript Closures: The Missing Piece Before React Re-rendering

Session 18 named your event handlers. Session 19 is about to show you that every render creates brand new versions of those handlers, each one frozen with its own copy of count. That sentence only makes sense if you already know what a closure is — and until now, we've never actually stopped to explain it. This short detour is pure JavaScript, no React required, and it's the one idea that makes everything in Session 19 click instead of feeling like memorized trivia.

Estimated time: 25–30 minutes

1. Learning Objectives

  • Explain what happens every time JavaScript calls a function — a brand new execution context with its own local variables
  • Describe lexical scope: how an inner function can read variables from the outer function it was written inside
  • Define a closure in plain English and use the phrase "this function closes over this variable" correctly
  • Prove that calling the same outer function twice creates two completely independent closures, not one shared one
  • Connect closures to event handlers, and preview why every React render creates brand new closures of its own

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

function outer() { let x = 0; return function() { x++; return x; }; } — you call outer() once and store the returned function in fn. What does fn() return the first two times you call it?

The returned function keeps a live reference to x, not a snapshot — each call increments the same remembered variable.
Question 2 of 5

Same outer() from above. You call it a second time and store the result in fn2. You then call fn() three more times and fn2() once. What does fn2() return?

Each call to outer() creates a brand new x. fn and fn2 are two totally separate closures over two totally separate variables.
Question 3 of 5

A local variable declared inside a function normally disappears the moment the function returns. What keeps it alive when a closure is involved?

Something being reachable is what keeps it alive. A closure is exactly that: a live reference held by an inner function.
Question 4 of 5

A button's onClick handler reads a variable from the function it was defined inside. That outer function already finished running long ago. Will the handler still work when the button is finally clicked?

This is the entire mechanism behind every event handler you've written since Session 17, whether or not you noticed it.
Question 5 of 5

Every time React calls your component function during a render, does it reuse the exact same handler function objects from last time, or build new ones?

Calling a function again always creates new local functions inside it — a component function is no exception, which is the whole setup for Session 19.

3. The Concept — Functions, Scope, and What Gets Remembered

Every function call starts completely fresh

In C#, calling a method twice is unremarkable — you already know each call gets its own stack frame and its own local variables. JavaScript works the same way, but it's worth saying explicitly because closures only make sense once this is second nature: every single time JavaScript calls a function, it creates a brand new, private set of local variables for that call. Nothing from a previous call leaks in. 

function greet(name) {
  let message = `Hello, ${name}`;   // brand new "message" every call
  console.log(message);
}

greet("Priya");  // "Hello, Priya" — its own message
greet("Sam");    // "Hello, Sam" — a completely different message

Execution context: the technical name for "a fresh run"

The formal term for one of these fresh runs is an execution context. You don't need to memorize the term, but the shape is worth internalizing, because it's the exact shape a closure hooks into:

Step 4 is the important one. Once a function finishes, its local variables are normally gone — nothing outside can reach them anymore, so JavaScript is free to clean them up. Normally. There is one way to stop this from happening, and that's the entire subject of this lesson.

Lexical scope: how an inner function can see an outer variable

"Lexical" just means "based on where the code is physically written." If you write one function's definition inside another function's body, the inner one can read — not just guess at, actually read — any variable that exists in the outer function, without you doing anything special to wire it up. 

function outer() {
  let city = "Toronto";

  function inner() {
    console.log(city);   // inner can read outer's variable directly
  }

  inner();   // logs "Toronto"
}

outer();

Here's a second example, proving it isn't magic tied to one variable name — it works for any variable declared anywhere in the outer function, read anywhere inside the inner one:

function outer() {
  let a = 1;
  let b = 2;

  function inner() {
    console.log(a + b);   // inner can read BOTH outer variables
  }

  inner();   // logs 3
}

outer();

Notice what's not happening: inner never declares its own city, a, or b. It's reading the outer function's actual variables, live — this is lexical scope, and it's true the moment you nest one function inside another, whether or not the outer function has already returned.

Closures: the official definition, then plain English

Here's the formal definition you'll see in most JavaScript references:

A closure is the combination of a function bundled together with references to its surrounding lexical scope.

In plain English:

A closure simply means a function remembers the variables that existed when it was created — even after the function that created those variables has already finished running.

There's a specific phrase JavaScript developers use for this, and it's worth knowing because you'll see it in real code reviews and documentation: "this function closes over this variable." In the example above, we'd say inner "closes over" city. That's not casual slang — it's the actual technical term. 

function outer() {
  let x = 0;

  return function increment() {
    x = x + 1;
    return x;
  };
}

const fn = outer();   // outer() runs once, then finishes...
console.log(fn());    // ...but increment still remembers x. Logs 1
console.log(fn());    // Logs 2
console.log(fn());    // Logs 3

outer() has already returned by the time you call fn() the first time. Its execution context, by the rule from Section 3.2, should have been discarded. But it wasn't — because increment still holds a live reference to x, JavaScript keeps x around instead of throwing it away. That's the whole trick. Nothing else is going on.

Every call to the outer function makes a brand new closure

This next part is the single most important idea in this session, and it's the exact thing Session 19 needs from you. Calling outer() a second time does not reuse the first x — it creates an entirely new execution context (Section 3.2 again), with its own entirely new x, and the function it returns closes over that one instead. 

const counterA = outer();   // creates its own private x, starting at 0
const counterB = outer();   // creates a SEPARATE, independent x, starting at 0

console.log(counterA());   // 1
console.log(counterA());   // 2
console.log(counterB());   // 1 — completely unaffected by counterA

There is no shared state between counterA and counterB whatsoever. They happen to be built from the same function definition, but each call to outer() mints a fully independent closure with its own private copy of everything it closes over.

Event handlers are just ordinary functions that close over variables

Nothing about an event handler is special JavaScript syntax — it's an ordinary function, and it follows the exact same closure rule as everything above. When you attach a handler inside another function, it closes over whatever variables that outer function had at the time. 

function setupButton(name) {
  const button = document.querySelector("button");

  button.onclick = function handleClick() {
    console.log(`Hello from ${name}`);   // closes over "name"
  };
}

setupButton("Priya");
// Click the button any time later — even minutes later — it still
// logs "Hello from Priya". setupButton already finished running long
// ago, but handleClick's closure kept "name" alive.

This is exactly what's been happening since Session 17's very first onClick. It felt like ordinary React, but underneath it was ordinary JavaScript closures the entire time.

React preview: every render makes new closures too

A React component is, underneath everything, just a function. Section 3.1 already told you what happens every time a function gets called: a brand new execution context, with brand new local variables. React re-rendering a component is calling that function again — so every render creates a brand new handleClick, closing over that render's own local count, completely independent from the handleClick and count from the render before it.

Not required today, previewed for Session 19: this is exactly why calling a state setter twice in one handler doesn't do what you might expect (a "stale closure"), why React batches multiple updates into a single re-render, and why a "functional update" like setCount(c => c + 1) sidesteps the whole problem by reading the latest value instead of a remembered one. You don't need to understand any of those three things yet — you only need to know that closures are the mechanism underneath all three, which you now do.

4. Lab

Lab objective: Write a plain JavaScript closure from scratch, prove it remembers a variable, then prove that calling its outer function twice produces two independent closures — no React involved yet.
1

Create the lab file and write an outer function that returns an inner one

// src/labs/closures.js
function makeCounter() {
  let count = 0;

  return function increment() {
    count = count + 1;
    return count;
  };
}
2

Call it once, and prove the returned function remembers count

const counter1 = makeCounter();

console.log(counter1());   // expect 1
console.log(counter1());   // expect 2
console.log(counter1());   // expect 3
3

Call makeCounter() a second time, and prove the two closures are independent

const counter2 = makeCounter();

console.log(counter2());   // expect 1 — NOT 4, its own fresh count
console.log(counter1());   // expect 4 — counter1's count kept going, unaffected
4

Run it and read the output

node src/labs/closures.js

Confirm the console output matches the comments exactly: 1, 2, 3, then 1, then 4. If counter2() printed 4 instead of 1, the two closures aren't actually independent — double-check count is declared fresh inside makeCounter, not somewhere shared outside it.

5

Now the tiny React connection — read only, no file changes required

Open src/component/CountryCard.jsx from Session 18 and look at handleClick. It reads count without ever declaring it — exactly like inner reading city back in Section 3.3. And exactly like counter1 and counter2 above, every time CountryCard runs again, it builds a brand new handleClick that closes over that particular run's own count. 8. Post-Coding Quiz

Question 1 of 5

You call makeCounter() once into counter1, call counter1() three times, then call makeCounter() again into counter2 and call it once. What does counter2() return?

Every call to makeCounter() creates a new execution context with its own count — closures never share state across separate outer calls.
Question 2 of 5

A plain local variable normally vanishes once its function returns. Why doesn't that happen to a variable a closure depends on?

Reachability is the deciding factor: if some live function still references a variable, JavaScript has no reason to discard it.
Question 3 of 5

Why do event handlers naturally close over variables without any special React syntax being involved?

This was the whole point of Section 6 — handlers get closures for free because they're just functions defined inside other functions.
Question 4 of 5

A React component function runs again on every re-render. Based on today's lesson, what does that imply about the event handlers it defines each time?

A render is just another function call — Section 7's exact rule applies: new call, new locals, new closures.
Question 5 of 5

Session 19 will show two setCount calls in one handler only incrementing count by 1, not 2. Based on today's lesson, what's the most likely underlying reason?

You don't need Session 19's full explanation yet — but you now have the exact vocabulary to predict it: both calls are reading the same remembered value from the same closure.

10. What Breaks If This Code Is Removed?

  • Return count directly instead of a function that reads it: You'd get a single number back, not a reusable counter — there would be nothing left to call a second time, and nothing demonstrating a closure at all.
  • Declare count outside makeCounter, at module level: counter1 and counter2 would suddenly share the exact same count, and calling either one would affect the other — the opposite of what this lab is meant to prove.
  • Call makeCounter() only once and reuse its result everywhere: You'd never observe two independent closures, only ever see one — the single most important lesson of this session would go unverified.

11. What React Concept Was Learned Today

Today you learned: a closure is a function that remembers the variables that existed when it was created, calling the same outer function twice always produces two independent closures, and event handlers — including every one you've written in this course — get this behavior for free because they're ordinary JavaScript functions. React didn't invent any of this; it just calls your component function again on every render, and JavaScript's own closure rules do the rest.
