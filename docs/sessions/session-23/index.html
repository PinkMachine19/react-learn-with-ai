Why Mock Data Matters

A frontend should not wait for a backend before its screens, states, and data contract can be designed. Today you create a realistic JSON fixture that becomes the agreed shape of a country.

Estimated time: 45–55 minutes · New file: mock/countries.json

1. Learning Objectives

  • Explain why mock data lets frontend work continue independently
  • Distinguish realistic fixtures from random placeholder values
  • Describe a data contract as field names, types, and meaning
  • Create valid JSON with stable unique identifiers
  • Recognize what mocks can and cannot prove

2. Pre-Coding Quiz

Answer before reading. Need 4/5 to proceed.

Question 1 of 5

What is the main purpose of mock data?

A mock is a temporary, controlled implementation of a contract. It supports development; it does not prove the real API works.
Question 2 of 5

Which property is best suited for a React list key?

A stable unique id preserves identity when order or contents change, as learned in Session 15.
Question 3 of 5

What makes JSON different from a JavaScript object literal?

JSON is language-independent text. Functions, comments, undefined, and trailing commas are not valid JSON.
Question 4 of 5

A country has no known population. Which contract decision is clearest?

Consistency is the contract. Consumers need to know whether a field is required, optional, or nullable.
Question 5 of 5

What does a working UI with mock data prove?

Mocks only prove behavior for the cases represented. Real integration still needs testing.

3. The Concept — Contract First

A useful mock is executable documentation

A sentence such as “the API returns countries” leaves important questions unanswered. A fixture makes decisions visible: Is id a number or string? Is the field called name or commonName? Is population numeric? The component and future API can now target the same shape.

{
  "id": 1,
  "name": "Canada",
  "region": "Americas",
  "population": 40097761
}

Use realistic variety, not only happy-path clones

Ten identical-looking rows hide UI problems. Include multiple regions, short and long names, small and large populations, while keeping every value plausible and every object structurally consistent.

Boundary: Mock data removes a scheduling dependency, not an integration requirement. It does not simulate latency, HTTP status codes, authentication, or an evolving production API. Session 25 introduces fake timing; later layers introduce real fetching and failures.

4. Lab

Lab objective: Create mock/countries.json with ten valid, consistently shaped countries.
1

Create the mock folder and JSON file

Create mock/countries.json at the repository root. This fixture is intentionally separate from src/data/countries.js: it documents the future external contract.

2

Add ten countries

[
  { "id": 1, "name": "Canada", "region": "Americas", "population": 40097761 },
  { "id": 2, "name": "Japan", "region": "Asia", "population": 124516650 }
]

Continue to ten objects. Each id must be unique; every object must use the same four fields and value types.

3

Validate the JSON

node -e "JSON.parse(require('fs').readFileSync('mock/countries.json','utf8')); console.log('valid JSON')"

Fix missing commas, single quotes, comments, or trailing commas if parsing fails.

4

Inspect the contract

Verify unique ids, at least three regions, numeric populations, and exact property spelling. Do not wire the fixture into React yet; Session 24 adds the access boundary.

8. Post-Coding Quiz

Question 1 of 5

Why keep a mock fixture separate from components?

Separation gives data a clear home and prepares for the service boundary in Session 24.
Question 2 of 5

Which change breaks the agreed contract?

A consumer expecting region receives undefined for the inconsistent object.
Question 3 of 5

Why include realistic edge variety?

Varied fixtures reveal truncation, filtering, formatting, and empty-state assumptions early.
Question 4 of 5

Why is population: "40097761" a concern if the contract says number?

A numeric-looking string is still a string, so arithmetic and comparison semantics differ.
Question 5 of 5

What is the next architectural step?

Session 24 creates one boundary that callers use regardless of where data comes from later.

9. Reflection Questions

  1. Which contract decision would be most expensive to change after several components depend on it?
  2. What edge case is not represented in your ten-country fixture?
  3. What can a mock prove, and what still requires real integration?

10. What Breaks If This File Is Removed?

  • The shared example contract disappears.
  • Frontend work must depend on another data source or duplicate values.
  • Session 24 has no controlled fixture to place behind its service boundary.

11. What Engineering Concept Was Learned Today

Mock data is a controlled implementation of a data contract that enables parallel development and faster iteration.
