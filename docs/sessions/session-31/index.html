Testing the Service Layer

Test asynchronous service contracts independently: control imported country data, await Promise outcomes, assert returned shapes, and distinguish an empty collection from a rejected singular lookup.

Layer 5 gate: score ≥ 80% on the post-quiz before continuing.

1. Learning Objectives

  • Mock an imported data dependency with vi.mock
  • Await resolved and rejected Promise assertions
  • Assert Country array shape without duplicating the fixture
  • Distinguish empty collection success from singular lookup failure
  • Use fake timers without racing pending Promises

2. Pre-Coding Quiz

Need 4/5 to proceed.

Question 1 of 5

Why mock the imported country data in a service unit test?

Controlled dependency input isolates service behavior and avoids coupling expectations to the full fixture.
Question 2 of 5

Which assertion correctly checks a rejected lookup Promise?

The rejects chain unwraps the rejected Promise and applies the error matcher.
Question 3 of 5

What should a no-match region query resolve to?

Collection queries can successfully return zero members while preserving an array return type.

3. The Concept — Test the Boundary, Control the Dependency

vi.mock('../data/countries.js', () => ({
  default: [
    { id: 1, name: 'Japan', region: 'Asia', population: 1 }
  ]
}));

Vitest hoists vi.mock, so values used by its factory should be declared inside the factory (or with vi.hoisted). Use the service’s actual exported names—currently fetchAllCountries, fetchAllById, and fetchAllByRegion—rather than inventing a generic getAll API.

4. Lab

Lab objective: Test fulfilled collections, singular rejection, filtering, and Promise timing in the country service.
End state: Controlled fixture input exercises real service logic for success, empty results, and errors.
1

Mock only fixture data

Keep filtering, copying, delays, and errors real.

import { afterEach, expect, test, vi } from 'vitest';

vi.mock('../data/countries', () => ({
  default: [
    { id: 1, name: 'Canada', region: 'Americas', population: 50000000 },
    { id: 2, name: 'Japan', region: 'Asia', population: 150000000 }
  ]
}));

import {
  getCountries,
  getCountryById,
  getCountriesByRegion
} from './countryServices.js';

afterEach(() => vi.useRealTimers());
2

Assert the collection

Check shape and a fresh outer array.

test('getCountries resolves a fresh Country array', async () => {
  const first = await getCountries();
  const second = await getCountries();

  expect(first).toHaveLength(2);
  expect(first[0]).toEqual({
    id: 1, name: 'Canada',
    region: 'Americas', population: 50000000
  });
  expect(first).not.toBe(second);
});
3

Test known and unknown IDs

Prove both singular outcomes.

test('known id resolves', async () => {
  await expect(getCountryById(2)).resolves.toMatchObject({
    id: 2, name: 'Japan'
  });
});

test('unknown id rejects', async () => {
  await expect(getCountryById(999)).rejects.toThrow(
    'Country 999 not found'
  );
});
4

Test matching and empty regions

Collections fulfill consistently.

test('region returns matches', async () => {
  await expect(getCountriesByRegion('Asia')).resolves.toEqual([
    { id: 2, name: 'Japan', region: 'Asia', population: 150000000 }
  ]);
});

test('unknown region returns []', async () => {
  await expect(getCountriesByRegion('Oceania')).resolves.toEqual([]);
});
5

Control Promise timing

Advance the documented delay and restore timers.

test('getCountries waits 300ms', async () => {
  vi.useFakeTimers();

  const assertion = expect(
    getCountries()
  ).resolves.toHaveLength(2);

  await vi.advanceTimersByTimeAsync(300);
  await assertion;
});

Question 1 of 5

A mocked source contains two countries, but get-all resolves to the same array reference. Which contract concern can a test expose?

Reference identity matters when the service promises a protective outer-array copy.
Question 2 of 5

Why await expect(promise).resolves rather than only creating the expectation?

Without awaiting or returning the chain, a test can finish before the assertion settles.
Question 3 of 5

A region filter returns []. Which expectation matches the collection contract?

No matches is a successful empty collection, not an operational failure.
Question 4 of 5

A test mocks the service itself while claiming to test service filtering. What is the problem?

Mock dependencies of the unit, not the unit behavior being verified.
Question 5 of 5

These tests protect distinct observable boundaries: initial UI, stateful behavior, and asynchronous data access.

9. Reflection Questions

  1. Which service dependency should be controlled and which behavior must remain real?

    Control the imported fixture or external data dependency so inputs are deterministic. Keep the service's filtering, copying, Promise timing, and rejection logic real because those behaviors are the unit under test.

  2. Why do empty collection and missing singular entity use different outcomes?

    A collection query can successfully contain zero matches, so it resolves to an empty array. A singular lookup promises one entity; when none exists, rejection clearly communicates that the requested result is missing.

  3. What bug could fake timers accidentally hide if used carelessly?

    Advancing every timer immediately without asserting the pending phase can hide an incorrect delay or ordering dependency. Broad timer flushing can also mask scheduling bugs that would appear with realistic asynchronous progression.

10. What Breaks If Service Tests Are Removed?

  • Promise shape and failure regressions can reach UI callers.
  • Filtering behavior can drift silently.
  • Fixture changes may alter contracts without focused feedback.

11. What Engineering Concept Was Learned Today

Service tests control external inputs while exercising real asynchronous behavior and asserting the public data contract.
