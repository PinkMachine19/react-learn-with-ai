Layer 3 Session 22 — Layer 3 Gate State

Derived State

App.jsx already computes filteredCountries fresh on every render instead of storing it in its own useState — you did this "correctly" back in Session 21 without it being named yet. Today we name it, prove why the alternative is a real bug waiting to happen, and formalize the rule: if a value can be calculated from state you already have, it should be, not stored again.

Layer 3 gate: Post-quiz ≥ 80% required. Review Sessions 16–21 if needed.
Estimated time: 35–40 minutes

1. Learning Objectives

  • Define "derived state": a value computed from existing state during render, instead of stored in its own state
  • Explain why storing a computable value in its own useState creates a real risk of it drifting out of sync
  • Recognise that App.jsx's filteredCountries has been a derived value since Session 21, without the term being used yet
  • Fix a genuine bug in the current filter (case sensitivity) while keeping it derived, not stateful
  • Add a second derived value — a result count — computed from the first derived value

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed (Layer gate — this quiz counts toward your Layer 3 score).

Question 1 of 5

What does "derived state" mean?

A derived value is computed fresh each render from state that already exists — it has no useState of its own.
Question 2 of 5

Since Session 21, App.jsx has had this line: const filteredCountries = countries.filter(c => c.name.includes(searchTerm));. Is filteredCountries state?

Changing over time isn't what makes something state — being created and updated via useState is. filteredCountries just gets recalculated, from scratch, on every render.
Question 3 of 5

Suppose, instead, App had written const [filteredCountries, setFilteredCountries] = useState(countries) and updated it manually inside handleSearchChange alongside searchTerm. What real risk does this introduce that the derived version doesn't have?

This is the entire motivating risk: two independent pieces of state that are supposed to represent related information can drift apart the moment one update site is missed.
Question 4 of 5

Searching "kenya" (lowercase) currently returns no results even though "Kenya" exists in the data. Why?

This is a real, fixable bug in the current filter — the fix is still a derived calculation, just with .toLowerCase() applied to both sides of the comparison.
Question 5 of 5

Which value is genuinely real state in App — something that cannot be calculated from anything else?

searchTerm is the one true independent value — everything else in this session (filteredCountries, resultCount) can be recalculated from it plus the imported countries array.

3. The Concept — Compute It, Don't Store It

The anti-pattern, for contrast (not what App.jsx does)

// RISKY — do not do this. Shown only to name the risk clearly.
const [searchTerm, setSearchTerm] = useState('');
const [filteredCountries, setFilteredCountries] = useState(countries);

function handleSearchChange(event) {
  const value = event.target.value;
  setSearchTerm(value);
  setFilteredCountries(countries.filter(c => c.name.includes(value)));
  // Two update calls, in two places, that must ALWAYS be kept in lockstep.
  // Add a second place that updates searchTerm later, forget to update
  // filteredCountries there too, and the two silently disagree.
}

This isn't hypothetical laziness — it's a genuinely tempting thing to write, especially coming from other UI frameworks. It even works, today, with exactly one update site. The risk is entirely about the future: every additional place that needs to change searchTerm now also has to remember to update filteredCountries in lockstep, forever.

What App.jsx has actually been doing since Session 21

function App() {
  const [searchTerm, setSearchTerm] = useState('');

  function handleSearchChange(event) {
    setSearchTerm(event.target.value);   // ONE update site, ONE piece of real state
  }

  const filteredCountries = countries.filter(c =>
    c.name.includes(searchTerm)
  );
  // Recalculated from scratch, every single render.
  // There is nothing to keep "in sync" — it's freshly correct every time.
}

There is no second useState, and there is nothing to forget to update. filteredCountries cannot become stale, because it is never stored anywhere between renders — it's rebuilt from searchTerm and countries every time App runs.

A real bug in today's filter: case sensitivity

String.prototype.includes() is case-sensitive. "Kenya".includes("kenya") is false, because the lowercase "k" doesn't match the uppercase "K" character for character. Fixing this is still a purely derived calculation — no state is needed, just a more careful comparison: 

const filteredCountries = countries.filter(c =>
  c.name.toLowerCase().includes(searchTerm.toLowerCase())
);

Deriving a value from a derived value

Nothing stops a derived value from being built on top of another derived value. resultCount doesn't need its own state either — it's just the length of the array we already computed: 

const resultCount = filteredCountries.length;

return (
  <div>
    <h1>Countries</h1>
    <input value={searchTerm} onChange={handleSearchChange} />
    <p>{resultCount} {resultCount === 1 ? 'result' : 'results'}</p>
    <CountryList countries={filteredCountries} />
  </div>
);
The actual test to apply: before reaching for useState, ask "can I calculate this from state I already have?" If yes, it's derived — write it as a plain const during render. Reach for useState only for the genuinely independent piece of information that nothing else can produce — here, that's only ever searchTerm.

8. Post-Coding Quiz

Question 1 of 5

If you added const [resultCount, setResultCount] = useState(0) and manually called setResultCount inside handleSearchChange, what mistake would this repeat?

Exactly the same risk as storing filteredCountries separately — now there's a third value that could theoretically drift out of sync.
Question 2 of 5

"Kenya".toLowerCase() returns what?

toLowerCase() is a plain string method, usable on any string value including literals — it returns a new all-lowercase string.
Question 3 of 5

How many useState calls does App have after today's session, total?

searchTerm remains the single genuine piece of state. Both filteredCountries and resultCount are computed from it plus the imported countries array.
Question 4 of 5

Why can't filteredCountries and resultCount ever disagree with each other, the way a stored/derived pair could?

Since resultCount reads directly from filteredCountries in the same function call, there's no window in which they could show different, inconsistent information.

10. What Breaks If This Code Is Removed?

  • Revert to case-sensitive matching: Searching "kenya" (or any lowercase-typed name) fails to find "Kenya" — a real, user-facing bug, not just a style issue.
  • Remove resultCount entirely: No functional loss — it's a display convenience. The list itself still filters correctly without it.
  • Store filteredCountries or resultCount in their own useState: Reintroduces exactly the sync-drift risk this whole session exists to prevent — code that works today but is one missed update site away from silently showing the wrong thing.

11. What React Concept Was Learned Today

Today you learned: a value that can be calculated from existing state should be computed fresh during render as a plain const, not stored in its own useState — this guarantees it can never drift out of sync with the state it's derived from.
