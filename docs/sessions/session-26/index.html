Designing Against a Contract

Turn the implicit country shape into an explicit JSDoc contract, then check that fixtures, services, and components agree on the same vocabulary.

Layer 4 gate: score ≥ 80% on the post-quiz before starting the testing layer.

1. Learning Objectives

  • Express the Country shape with a JSDoc typedef
  • Document required, optional, array, and Promise return types
  • Separate static documentation from runtime validation
  • Audit fixtures and services for contract drift
  • Explain why contract changes require coordinated migration

2. Pre-Coding Quiz

Need 4/5 to proceed.

Question 1 of 5

A service resolves to an array later. Which annotation describes both timing and shape?

The annotation identifies asynchronous delivery and the element contract of the resolved collection.
Question 2 of 5

The fixture uses population, but one record uses populaton. What failed?

Valid JSON can still violate an application contract through a misspelled property.
Question 3 of 5

What does JSDoc do when malformed API data arrives at runtime?

JSDoc supports documentation and tooling; comments do not execute validation logic.
Question 4 of 5

Which JSDoc property marks capital as optional?

Brackets around the property name indicate that the property itself may be absent.
Question 5 of 5

Two teams agree that population is a number but disagree whether it means people or thousands of people. What is missing?

Contracts include meaning and units, not only field names and primitive types.

3. The Concept — Make Assumptions Explicit

Session 23 created a contract by example. JSDoc gives that shape a reusable name:

/**
 * @typedef {Object} Country
 * @property {number} id - Stable unique identifier.
 * @property {string} name - Display name.
 * @property {string} region - Region used by filters.
 * @property {number} population - Number of people.
 */

Functions can now communicate their public boundary without changing runtime behavior:

/** @returns {Promise<Country[]>} */
export async function fetchAllCountries() { /* existing implementation */ }

/**
 * @param {number} id
 * @returns {Promise<Country>}
 */
export async function fetchAllById(id) { /* existing implementation */ }
Important: this session documents existing behavior. It does not add TypeScript, schema validation, or a new API.

8. Post-Coding Quiz

Question 1 of 5

A caller sorts the result of fetchAllCountries(). Which contract detail is most relevant before the sort?

The caller needs to know it will receive a collection whose members follow the Country shape.
Question 2 of 5

The contract changes population from people to millions. What is the safe migration?

A semantic contract change must migrate every participant that produces, transforms, tests, or displays the value.
Question 3 of 5

Which finding proves the fixture violates @property {number} population?

Quotation changes the runtime primitive from number to string, directly violating the declared type.
Question 4 of 5

An id lookup rejects when no country exists. Where should that failure behavior be documented?

Rejection behavior is observable to callers and belongs in the operation contract.
Question 5 of 5

Why can a fully annotated service still return malformed live data?

Static assistance and runtime validation solve different problems; comments do not inspect live values.

9. Reflection Questions

  1. Which assumption in the current fixture was easiest to miss before writing the typedef?
  2. What would require runtime validation rather than JSDoc?
  3. Which service behavior beyond the successful value belongs in its contract?

10. What Breaks If the Contract Is Removed?

  • Field assumptions return to scattered examples and memory.
  • Editor assistance cannot connect services to consumers.
  • Contract drift becomes harder to notice during review.

11. What Engineering Concept Was Learned Today

A contract makes data shape, meaning, timing, and failure assumptions explicit across system boundaries.
