Designing Against a Contract

Turn the implicit country shape into an explicit JSDoc contract, then check that fixtures, services, and components agree on the same vocabulary.

Layer 4 gate: score ≥ 80% on the post-quiz before starting the testing layer.

1. Learning Objectives

  • Express the Country shape with a JSDoc typedef
  • Document required, optional, array, and Promise return types
  • Separate static documentation from runtime validation
  • Audit fixtures and services for contract drift
  • Explain why contract changes require coordinated migration

2. Pre-Coding Quiz

Need 4/5 to proceed.

The annotation identifies asynchronous delivery and the element contract of the resolved collection.
Question 2 of 5

Valid JSON can still violate an application contract through a misspelled property.
Question 3 of 5

Question 5 of 5

Contracts include meaning and units, not only field names and primitive types.

3. The Concept — Make Assumptions Explicit

Session 23 created a contract by example. JSDoc gives that shape a reusable name:

/**
 * @typedef {Object} Country
 * @property {number} id - Stable unique identifier.
 * @property {string} name - Display name.
 * @property {string} region - Region used by filters.
 * @property {number} population - Number of people.
 */

Functions can now communicate their public boundary without changing runtime behavior:

/** @returns {Promise<Country[]>} */
export async function fetchAllCountries() { /* existing implementation */ }

/**
 * @param {number} id
 * @returns {Promise<Country>}
 */
export async function fetchAllById(id) { /* existing implementation */ }
Important: this session documents existing behavior. It does not add TypeScript, schema validation, or a new API.

4. Lab

Lab objective: Define one explicit Country contract, attach it to every service operation, repair fixture records that violate it, and verify what the editor can—and cannot—guarantee.
End state: fixture records, Promise return annotations, and callers agree that every country has numeric id and population fields plus string name and region fields.
1

Define the Country shape and meaning

Place the typedef near the top of countryServices.js. Describe units and identifiers, not only JavaScript primitive types.

/**
 * One country record used by the service and UI.
 *
 * @typedef {Object} Country
 * @property {number} id - Unique numeric identifier.
 * @property {string} name - Display name of the country.
 * @property {string} region - Region used by filter operations.
 * @property {number} population - Number of people.
 */
2

Annotate parameters, fulfilled values, and failure

Collection operations resolve to arrays. The singular operation resolves to one Country or rejects when the requested ID is absent.

/** @returns {Promise<Country[]>} */
export async function getCountries() {
  await delay(300);
  return [...countries];
}

/**
 * @param {number} id
 * @returns {Promise<Country>}
 * @throws {Error} When no country has the requested id.
 */
export async function getCountryById(id) {
  await delay(150);
  const country = countries.find(item => item.id === id);

  if (!country) {
    throw new Error(`Country ${id} not found`);
  }

  return country;
}

/**
 * @param {string} region
 * @returns {Promise<Country[]>}
 */
export async function getCountriesByRegion(region) {
  await delay(200);
  return countries.filter(item => item.region === region);
}

Repair Africas, China’s incorrect region, and populaton. Keep every ID unique and every population numeric.

4

State the static-versus-runtime boundary

Record what the annotation provides and what must still be enforced when untrusted data enters the program.

// JSDoc gives editors and static analysis a shared Country contract.
// It can flag misspelled fields and incompatible caller assumptions.
//
// JSDoc does not execute when JSON or API data arrives.
// Runtime validation or focused tests must reject missing fields,
// wrong primitive types, invalid values, and duplicate identifiers.
5

Verify the contract from a caller

Enable JavaScript checking, consume the typed result, and deliberately try one misspelled property to see the editor warning.

// @ts-check
import { getCountryById } from './countryServices.js';

async function verifyCountryContract() {
  const country = await getCountryById(1);

  console.log(country.name);
  console.log(country.population);

  // Uncomment to verify the editor catches contract drift:
  // console.log(country.populaton);
}

verifyCountryContract();

7. Code Review Checklist

8. Post-Coding Quiz

Question 1 of 5

A caller sorts the result of fetchAllCountries(). Which contract detail is most relevant before the sort?

The caller needs to know it will receive a collection whose members follow the Country shape.
Question 2 of 5

The contract changes population from people to millions. What is the safe migration?

A semantic contract change must migrate every participant that produces, transforms, tests, or displays the value.
Question 3 of 5

Which finding proves the fixture violates @property {number} population?

Quotation changes the runtime primitive from number to string, directly violating the declared type.
Question 4 of 5

An id lookup rejects when no country exists. Where should that failure behavior be documented?

Rejection behavior is observable to callers and belongs in the operation contract.
Question 5 of 5

Why can a fully annotated service still return malformed live data?

Static assistance and runtime validation solve different problems; comments do not inspect live values.

9. Reflection Questions

  1. Which assumption in the current fixture was easiest to miss before writing the typedef?

    The easiest assumptions to miss are inconsistent field names, spelling, or allowed values because examples can look correct at a glance. Writing the typedef forces every record to use one explicit shape and vocabulary.

  2. What would require runtime validation rather than JSDoc?

    Values arriving from files, storage, user input, or an API need runtime checks for required fields, types, ranges, and allowed values. JSDoc improves editor analysis but does not execute or reject invalid data.

  3. Which service behavior beyond the successful value belongs in its contract?

    The contract should include asynchronous timing, rejection conditions and error shape, how absence is represented, and whether returned collections are copies that callers may safely reorder.

10. What Breaks If the Contract Is Removed?

  • Field assumptions return to scattered examples and memory.
  • Editor assistance cannot connect services to consumers.
  • Contract drift becomes harder to notice during review.

11. What Engineering Concept Was Learned Today

A contract makes data shape, meaning, timing, and failure assumptions explicit across system boundaries.
