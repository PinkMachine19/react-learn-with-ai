Loading and Error States

Design asynchronous UI as explicit states so learners never see a blank screen, stale failure, or contradictory messages.

Estimated time: 50–65 minutes · Milestone: Add and test retry
Optional Warm-Up5-Minute Wake-Up Challenge: Name the UI State

Give yourself five minutes. Derive exactly one visible state from status and data instead of juggling unrelated booleans. Use a scratch file, Node REPL, or browser console; no full React app run is required.

const cases = [{status:'loading', data:[]},{status:'success', data:[]},{status:'success', data:[{id:'GHA'}]},{status:'error', data:[]}];

function visibleState(entry) { /* loading, empty, content, or error */ }
// One defensible solution
function visibleState({ status, data }) {
  if (status === 'loading') return 'loading';
  if (status === 'error') return 'error';
  return data.length === 0 ? 'empty' : 'content';
}
The four inputs resolve to loading, empty, content, and error.

9. Reflection Questions

  1. Why prefer one status over several booleans?

    A single state prevents impossible combinations such as loading and error being true together.

  2. Why is empty distinct from error?

    The request succeeded; it simply produced zero matching records, so recovery guidance differs.

  3. What should retry reset first?

    Clear stale error information and enter loading so the learner sees immediate, accurate feedback.

10. What Breaks If This Boundary Is Ignored?

  • Responsibilities drift across unrelated modules.
  • Safe changes become harder to verify and explain.
  • Future learners inherit coupling without its original reasoning.

11. What Engineering Concept Was Learned Today

Reliable async UX makes every request phase explicit and every recovery path visible.
