Reusable Components

Extract one stable UI contract from real duplication, preserve native button behavior, and prove the refactor did not change what users can do.

Estimated time: 55–70 minutes · Milestone: extract and verify a shared Button used by CountryCard

Save and Reset share button semantics while their labels and handlers vary. Region badges share the same compact-label responsibility while their text or tone varies. A country card and checkout summary may look rectangular, but they represent different domain responsibilities; the search input and population display do not even share interaction semantics.

1. Learning Objectives

  • Distinguish stable reuse from accidental visual similarity
  • Define a small Button prop contract using children, variant, and native button props
  • Preserve accessibility and event behavior through extraction
  • Keep country-specific rules out of a shared UI primitive
  • Verify the refactor with existing behavior tests and a focused component test

2. Pre-Coding Quiz

Need 4/5 to proceed. Choose based on responsibility and behavior—not answer length.

Question 1 of 5

CountryCard contains Click Me and Reset buttons. What is the strongest reason to extract a shared Button?

Reuse is justified by a stable responsibility: render an accessible button and forward its interaction contract. The handlers do not need identical implementations; they are intentionally supplied by each caller.
Question 2 of 5

Which concern should remain inside CountryCard rather than move into a generic Button?

The count is feature behavior owned by CountryCard. A shared Button may deliver the click event, but knowing what a country click means would couple the primitive to one feature and prevent honest reuse.
Question 3 of 5

Why use children for the Button label?

children is a composition slot, not state or translation. Button controls the stable wrapper and semantics; callers provide meaningful content such as “Click Me,” “Reset,” or an icon plus text.
Question 4 of 5

Why forward remaining props with ...buttonProps?

A wrapper should not erase useful native behavior. Carefully forwarding button props keeps event handlers, keyboard semantics, disabled state, names, and ARIA attributes available without inventing a custom prop for each one.
Question 5 of 5

What must stay true after replacing the native buttons?

Extraction is a refactor, so observable behavior is the contract. Line count and speculative flexibility are weak measures; existing tests should continue proving that users can find, click, and reset the controls.

Guided Analysis 2 of 5

Create src/components/ui/Button.jsx

Use a native button, default its form behavior safely, and forward the remaining native props.

function Button({
  children,
  variant = 'primary',
  className = '',
  type = 'button',
  ...buttonProps
}) {
  const classes = `button button--${variant} ${className}`.trim();

  return (
    <button type={type} className={classes} {...buttonProps}>
      {children}
    </button>
  );
}

export default Button;

type="button" prevents an accidental form submission when this component is later used inside a form. Callers can still explicitly pass type="submit".

Guided Analysis 5 of 5

Prove the refactor and the primitive contract

First run the existing CountryCard tests. Then add one focused Button test for prop forwarding.

// src/components/ui/Button.test.jsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { expect, test, vi } from 'vitest';
import Button from './Button.jsx';

test('forwards native button behavior', async () => {
  const user = userEvent.setup();
  const onClick = vi.fn();

  render(<Button onClick={onClick}>Save</Button>);
  await user.click(screen.getByRole('button', { name: 'Save' }));

  expect(onClick).toHaveBeenCalledOnce();
});

This test checks the shared contract once. CountryCard tests remain responsible for proving increment and reset behavior.

7. Code Review Checklist

8. Post-Coding Quiz

Question 1 of 5

After extraction, Reset looks correct but submits a surrounding form. Which contract detail was missed?

A native button defaults to submit when placed inside a form. Defaulting the wrapper to type="button" prevents surprising behavior while still allowing a caller to request type="submit".
Question 2 of 5

A caller passes disabled, but the rendered element stays clickable. What is the likely design flaw?

disabled only affects behavior when it reaches the native button. A wrapper that consumes or drops unknown props silently narrows the platform contract and forces callers to invent workarounds.
Question 3 of 5

Which test belongs in CountryCard.test.jsx rather than Button.test.jsx?

Resetting the count is a CountryCard feature rule. Button tests should protect the reusable delivery mechanism; feature tests should protect the meaning assigned to that mechanism.
Question 4 of 5

Two cards share a border and padding but contain unrelated workflows. What should you do first?

Visual similarity alone can produce a component full of modes and conditionals. First determine whether the elements share responsibility, behavior, and reasons to evolve; otherwise share a CSS token instead of a component.
Question 5 of 5

Why rerun CountryCard tests after adding a focused Button test?

A unit can satisfy its own contract while a caller imports it incorrectly, passes the wrong handler, or changes an accessible name. The focused test and feature tests protect different boundaries.

9. Reflection Questions

  1. Which Button decisions are stable enough to centralize, and which remain caller decisions?

    Button can centralize native button semantics, a safe default type, base styling, and named visual variants. Callers retain the label, event meaning, disabled condition, form intent, and domain behavior because those vary by use case.

  2. Why is a shared Button more than copied CSS?

    It preserves a behavioral and accessibility contract as well as appearance. Centralizing the native element, prop forwarding, type default, disabled behavior, and focus treatment prevents callers from rebuilding those details inconsistently.

  3. What evidence would tell you not to extract Card yet?

    If the candidate cards only share a border while their semantics, content structure, interactions, and reasons to change differ, a component would encode accidental similarity. Share design tokens or CSS first and wait for a stable API to emerge.

10. What Breaks Without a Stable Reuse Contract?

  • A generic component accumulates feature flags and becomes harder to understand than the duplicated markup.
  • Native capabilities disappear when wrappers fail to forward props.
  • Feature behavior leaks into shared UI and couples unrelated parts of the app.
  • Refactors appear successful while accessible names or interactions silently change.

11. What Engineering Concept Was Learned Today

Reusable components centralize a proven, stable contract while leaving domain meaning with the caller.
