Setting Up Vitest + React Testing Library

Build the smallest reliable test environment: Vitest runs tests, jsdom supplies browser-like DOM APIs, and React Testing Library renders components through their public output.

Estimated time: 45–60 minutes · Milestone: CountryCard smoke test
Optional Warm-Up5-Minute Wake-Up Challenge: Repair the Test Bench

Give yourself five minutes. Diagnose a deliberately incomplete Vitest setup before reading the configuration lesson. Run or revise the snippet repeatedly while you work.

No full app run required: use a separate scratch file, the VS Code/Node REPL, or the browser console—whichever creates the least friction.
// vite.config.js — in the project root, beside package.json
import { defineConfig } from 'vitest/config';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  test: {
    environment: "node"
  }
});

// CountryCard.test.jsx
test("renders a card", () => {
  render(<CountryCard name="Japan" region="Asia" />);
  expect(
    screen.getByRole("heading", { name: "Japan" })
  ).toBeInTheDocument();
});

// Current failures:
// 1. document is not defined
// 2. toBeInTheDocument is not a function

Your task: Identify the two setup changes needed to provide a DOM and install the custom DOM matcher.

// vite.config.js — in the project root, beside package.json
import { defineConfig } from 'vitest/config';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  test: {
    environment: "jsdom",
    setupFiles: "./test/setup.js"
  }
});

// test/setup.js
import "@testing-library/jest-dom/vitest";
import { cleanup } from "@testing-library/react";
import { afterEach } from "vitest";

afterEach(cleanup);
Lesson connection: You just matched each failure to the correct layer: jsdom supplies document, and jest-dom extends expect with DOM-specific matchers.

3. The Concept — Three Tools, Three Jobs

npm install -D vitest jsdom @testing-library/react @testing-library/jest-dom @testing-library/user-event

Run this command from the project root. Vitest runs tests; jsdom supplies DOM globals; Testing Library renders and queries. Keep these responsibilities separate when diagnosing failures.

4. Lab

Lab objective: Install and configure the component-testing stack, then render CountryCard in a first smoke test.
End state: Vitest runs in jsdom, shared matchers load once, and one deterministic smoke test passes.

Where these files go

Start in the project root—the folder that contains package.json, vite.config.js, and src/. Paths beginning with test/ or src/ below are relative to that root.

your-react-project/
├── package.json              ← add test scripts here
├── vite.config.js            ← add the test configuration here
├── test/
│   └── setup.js              ← create this file
└── src/
    └── component/
        ├── CountryCard.jsx
        └── CountryCard.test.jsx  ← create beside CountryCard
Do not create a second Vite config. Open the existing root vite.config.js and update it. Keep the React plugin already present.

vite versus vitest/config

Both packages export a helper named defineConfig. The helper returns the configuration object; it does not run tests.

  • import { defineConfig } from 'vite' is the normal Vite-only import and understands Vite options such as plugins.
  • import { defineConfig } from 'vitest/config' extends that configuration typing with Vitest’s test section, including environment and setupFiles.

Because this single file configures both Vite and Vitest, replace the existing vite import with vitest/config. Keep react imported from @vitejs/plugin-react; that is a separate Vite plugin.

Step 1 of 5

Install test dependencies from the project root

Open the VS Code terminal in the folder containing package.json, then run this as one line. It works in PowerShell, Command Prompt, Bash, and zsh.

npm install -D vitest jsdom @testing-library/react @testing-library/jest-dom @testing-library/user-event
2

Step 2 of 5

Update the existing root vite.config.js

Replace its defineConfig import, preserve the React plugin, and add the test property. The complete file should look like this:

// vite.config.js
import { defineConfig } from 'vitest/config';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  test: {
    environment: 'jsdom',
    setupFiles: './test/setup.js'
  }
});

setupFiles: './test/setup.js' is resolved from the project root, so it points to the file created in Step 3.

3

Step 3 of 5

Create test/setup.js from the project root

Create a root-level test folder—not src/test—then create setup.js inside it. This file loads DOM matchers and cleans up after each test.

// test/setup.js
import '@testing-library/jest-dom/vitest';
import { cleanup } from '@testing-library/react';
import { afterEach } from 'vitest';

afterEach(cleanup);

Step 4 of 5

Add scripts to the existing root package.json

Merge these entries into the existing scripts object. Keep scripts such as dev, build, and lint; do not replace the whole file with this abbreviated example.

{
  "scripts": {
    "test": "vitest run",
    "test:watch": "vitest"
  }
}
5

Step 5 of 5

Create and run the smoke test beside CountryCard.jsx

Create src/component/CountryCard.test.jsx. Keeping a component test beside its component makes the import ./CountryCard.jsx resolve locally. If your project uses a different component folder, place the test beside the actual file and use that path.

// src/component/CountryCard.test.jsx
import { render } from '@testing-library/react';
import { test } from 'vitest';
import CountryCard from './CountryCard.jsx';

test('renders CountryCard with valid props', () => {
  render(<CountryCard name="Japan" region="Asia" />);
});

Run it from the project root

In the VS Code terminal, make sure you are in the folder containing package.json, then run:

npm test

This invokes the "test": "vitest run" script from Step 4. Vitest discovers files ending in .test.jsx, runs once, prints the result, and returns to the terminal.

Expected result: the output identifies CountryCard.test.jsx and reports 1 passed. A smoke test has no visible browser window; React renders into jsdom inside the test process.

What does 1 passed actually prove?

This test calls render(<CountryCard ... />) and passes when that call finishes without throwing an error.

It proves that:

  • Vitest discovered and executed the test file.
  • JSX transformation, React, jsdom, and Testing Library are connected correctly.
  • CountryCard.jsx can be imported and executed with the supplied props.
  • React can create the component’s DOM without crashing.

It does not yet prove that:

  • Japan or Region:Asia appears correctly.
  • The counter starts at zero or changes after a click.
  • The Click Me and Reset buttons behave correctly.
  • The component is visually styled or positioned correctly.

That narrow purpose is why this is called a smoke test: it checks that the testing pipeline and component can start successfully. Session 29 adds assertions about visible output; Session 30 tests interaction and state.

Why does nothing display?

jsdom creates an in-memory document for the test. It is browser-like enough for DOM queries, but it does not open Chrome or display a page. The terminal’s pass/fail report is the normal result.

If you want to inspect the generated HTML while learning, temporarily import screen and call screen.debug():

import { render, screen } from '@testing-library/react';

test('renders CountryCard with valid props', () => {
  render(<CountryCard name="Japan" region="Asia" />);
  screen.debug();
});

Run npm test again and the rendered HTML will print in the terminal. screen.debug() is a diagnostic view, not an assertion, so remove it after inspecting the output.

For automatic reruns while editing, use:

npm run test:watch

Press q to leave watch mode. You do not need npm run dev to execute this test.

Quick troubleshooting
  • Missing script: test: merge the Step 4 entries into the scripts object in the root package.json.
  • No test files found: confirm the filename ends with .test.jsx and that the terminal is at the project root.
  • document is not defined: confirm environment: 'jsdom' is inside the test section of the root vite.config.js.
  • Cannot find ./test/setup.js: confirm the file is exactly test/setup.js at the project root.
  • Cannot resolve ./CountryCard.jsx: place the test beside the component or correct the relative import.

8. Post-Coding Quiz

Question 1 of 5

The smoke test fails before CountryCard executes because JSX cannot be transformed. Which layer is suspect?

A transform failure occurs before component behavior and points to build/test configuration.
Question 2 of 5

Why explicitly call cleanup after each test when not relying on globals?

Cleanup isolates tests by unmounting rendered trees and clearing their containers.
Question 3 of 5

Which failure is the smoke test designed to catch?

The smoke test only establishes successful rendering; later sessions protect output and interaction.
Question 4 of 5

A matcher says toBeInTheDocument is not a function. What is most likely missing?

toBeInTheDocument is supplied by jest-dom, not core Vitest.
Question 5 of 5

Why keep user-event installed even though the smoke test does not use it yet?

The testing sequence installs the interaction tool now and introduces its behavior later.

9. Reflection Questions

  1. Which tool owns each step from test discovery to DOM query?

    Vitest discovers and runs tests and assertions; jsdom provides the browser-like document; React Testing Library renders components and queries output; jest-dom adds DOM-specific matchers; user-event performs realistic interactions.

  2. What does the smoke test not prove?

    It proves only that the component can render without throwing in the configured environment. It does not verify correct content, accessibility, event handling, state changes, or edge cases.

  3. How would you diagnose a missing document differently from a render exception?

    A missing document points first to the test environment and jsdom configuration. If the DOM exists but rendering throws, inspect the component stack for import, prop, JSX, or application-logic failures.

10. What Breaks If Setup Is Removed?

  • Without jsdom, DOM rendering has no document.
  • Without setup, custom DOM matchers and explicit cleanup disappear.
  • Without scripts, test execution becomes inconsistent.

11. What Engineering Concept Was Learned Today

A component test needs a runner, a DOM environment, and a rendering/query library—each with a distinct responsibility.
