Layer 3 Session 21 State

Lifting State Up

Session 20 gave CountryList a working search box that nothing else could see. Today searchTerm moves to App — the nearest component that can see both the input and the list — and App does the filtering, passing only the matching countries down to CountryList as a prop.

Estimated time: 35–40 minutes

1. Learning Objectives

  • Identify the "nearest common ancestor" of two components that both need access to the same state
  • Move state (and the input that controls it) from a child component up to that ancestor
  • Filter a list using Array.prototype.filter() against a search term
  • Pass the filtered result down as a prop to a now-simpler, "presentational" child component
  • Explain why this move prevents the input and the list from ever disagreeing about the current search term

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

Why can't App read CountryList's local searchTerm state directly, before today's change?

This is the actual architectural constraint driving the whole session: state is private to the component that owns it, full stop.
Question 2 of 5

What does "lift state up" mean, precisely?

"Lifting" is literal — the useState call physically moves from the child's function body to the parent's.
Question 3 of 5

After lifting state up, what does CountryList's function signature look like?

CountryList doesn't need to know about searchTerm at all anymore — it just renders whatever countries array it's handed, exactly like CountryCard only knows its own name and region.
Question 4 of 5

Which array method correctly keeps only the countries whose name contains the search term?

filter() keeps every item for which the callback returns true and discards the rest, returning a new array — exactly what "narrow the list down" needs. map() would transform every item into a boolean instead of removing anything.
Question 5 of 5

Where does the <input> element itself live after today's change?

The input, its value, and its onChange all move together to wherever the state that controls it lives — App.

3. The Concept — Finding the Nearest Common Ancestor

The problem Session 20 left us with

searchTerm lives inside CountryList, created by CountryList's own useState call. State created this way belongs entirely to that component — nothing outside it, including its own parent App, can read or write it directly. There's no way for App to filter anything using a value it fundamentally cannot see.

The rule: state moves to the nearest shared ancestor

When two components both need the same piece of state, the fix is always the same: move the state up the tree until it lives in a component that is an ancestor of everything that needs it — here, that's App, since App renders CountryList directly.

App: state, handler, filter, and the input

import { useState } from "react";
import CountryList from "./component/CountryList";
import countries from "./data/countries";

function App() {
  const [searchTerm, setSearchTerm] = useState('');

  function handleSearchChange(event) {
    setSearchTerm(event.target.value);
  }

  const filteredCountries = countries.filter(c =>
    c.name.includes(searchTerm)
  );

  return (
    <div>
      <h1>Countries</h1>
      <input
        type="text"
        value={searchTerm}
        onChange={handleSearchChange}
        placeholder="Search countries..."
      />
      <CountryList countries={filteredCountries} />
    </div>
  );
}

Notice this is exactly the controlled-input code from Session 20 — value tied to state, onChange tied to a setter — just relocated. The only genuinely new line is the .filter() call, which builds a new array containing only the countries whose name includes the current search term.

CountryList: simplified down to props in, JSX out

import CountryCard from './CountryCard';

function CountryList({ countries }) {
  if (countries.length === 0) {
    return <p className='empty-message'>No countries found</p>
  }

  return (
    <section className='country-list'>
      {countries.map(c => (
        <CountryCard key={c.id} name={c.name} region={c.region}/>
      ))}
    </section>
  )
}

CountryList no longer imports the countries module, no longer calls useState, and no longer knows anything about searching. It receives a countries prop — already filtered or not, it can't tell the difference — and renders it. This kind of component, that only receives data and renders it without owning any logic, is often called "presentational."

Why this matters: before today, it would have been possible for the input to show one search term while the list somehow displayed something inconsistent with it, if a second copy of the state existed anywhere. After today, there is exactly one searchTerm in the entire app, and both the input and the filtering logic that feeds CountryList read from that single value.

7. Code Review Checklist

8. Post-Coding Quiz

Question 1 of 5

If CountryCard also needed to know the current searchTerm for some reason, where would you look to find it?

This previews "prop drilling" — passing a value down through a component that doesn't itself use it, just to reach a deeper child. Not something this session needs to solve, just recognise as the natural extension of the pattern.
Question 2 of 5

Why is CountryList now called a "presentational" or "dumb" component?

"Dumb" here isn't a quality judgment — it just means the component has no independent logic, making it easy to reuse and reason about in isolation.
Question 3 of 5

What would happen if CountryList still had its OWN leftover useState('') for searchTerm, in addition to receiving the filtered countries prop from App?

This is why the lab explicitly says to remove CountryList's own useState, not just add the new prop alongside it.
Question 4 of 5

Array.filter(callback) returns what, if zero items match the callback?

filter() always returns an array, even an empty one — which is exactly what makes CountryList's existing countries.length === 0 check work correctly with zero results.

9. Reflection Questions

  1. In your own words, what does "nearest common ancestor" mean, and why is it the right place for shared state to live?
  2. Why did moving searchTerm to App also mean moving the <input> element itself, not just the variable?

10. What Breaks If This Code Is Removed?

  • CountryList keeps importing countries directly instead of receiving the prop: The list would always show all 4 countries regardless of the search box — the input and the list would be completely disconnected again.
  • App forgets to pass countries={filteredCountries}: CountryList receives undefined for countries, and its countries.length check throws, since you can't read .length off undefined.
  • Filter logic uses .map() instead of .filter(): Every country would still render, just each one replaced by a true/false value instead of being included or excluded — the list would break entirely.

11. What React Concept Was Learned Today

Today you learned: when two components need the same state, it moves up to their nearest common ancestor, which owns it and passes derived results down as props — turning children into simpler, presentational components.
